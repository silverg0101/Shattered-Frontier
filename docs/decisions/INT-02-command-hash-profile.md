No `.proto`, executable fixture, package restore or runtime test accompanies this draft. Proposed identifiers below are profile/catalogue names, not registered endpoints.

## Proposed scoped boundary and exact framing

Define `F(label, parts...) = UTF8(label) || 00 || U32BE(count(parts)) || concat(U32BE(byte_length(p)) || p)`. Labels below are literal ASCII, `00` is one zero byte, lengths/counts are unsigned 32-bit big-endian, and each part is raw bytes. Reject oversized parts/counts rather than truncate. `S(x)` is strict UTF-8 without BOM, trimming, case folding or Unicode normalization; integer parts use the stated fixed-width representation. SHA256 outputs raw 32 bytes; `hex` means lowercase 64 ASCII hexadecimal digits.

1. A client boundary key is exactly 26 uppercase Crockford Base32 ULID characters (`[0-7][0-9A-HJKMNP-TV-Z]{25}`), representing at most 128 bits. Reject lowercase, surrounding whitespace and aliases; do not rewrite. Service/event keys retain Backend's deterministic grammar and registered IDs; this client restriction is not imposed on them.
2. Boundary scope is `(realm, actor_kind, actor_id, service, operation_family, original_key)`, all `S` parts. For initial player construction, `actor_kind` is literal `character` and `actor_id` is authenticated `chr_`; session/account admission remains separately verified. A new login must not manufacture another identity for the same character/key. Staff/system actor kinds are outside this initial profile pending owner definition. Realm and actor derive from approved trusted context, never merely a request body.
3. Proposed operation family is literal `CommitConstruction`, service is registered `building-service`. `K = "scope1:" || hex(SHA256(F("lsf/boundary-key/v1", scope parts)))`, 71 ASCII characters. Backend still stores `(rpc,K)` inside the owning service; `rpc` is its accepted fully qualified method identifier. Family-to-method binding is release-bound and immutable for this profile. No use across new methods without an explicit alias/migration contract.
4. Persist exact original scope/key, `K`, semantic profile/hash and action association in Building's action transaction. Unique original-scope and internal-key constraints must serialize concurrent admissions. On an occupied `K`, compare every original scope byte before replay: differing scope fails closed as a hash-collision invariant incident, never returns another principal's result or chooses a salted key. Same scope with changed intent rejects. Even a hypothetical equal semantic digest with unequal retained canonical semantic bytes fails closed; retention/compaction must preserve sufficient comparison evidence.
5. Participant flow key proposal: `cba:<action_id>:<step>`, with `<step> = hex(SHA256(F("lsf/delivery-step/v1", S(realm), S(incarnation), U64BE(generation), S(participant), S(phase))))`. Allowed phase literals are `prepare`, `decide`, `apply`, `complete`, `barrier`; actual RPC binding requires owner acceptance. Generation is 1…2^63−1. Store full step inputs and collision-check them too. Retry re-derives the key; new delivery authority changes it while retaining action/hash and historical decision. Current `cba_` ULID form yields 99 characters; still validate the 128-character bound rather than assume future IDs fit. These internal flow keys are not client boundary keys.

## Restricted protobuf serialization proposal P1

P1 is an application profile, not a claim about arbitrary protobuf. Pin proto3 descriptor bytes/hash, compiler/plugin binaries, language runtimes and profile revision with the accepted build. Future generated serializers must match the following rules or use a reviewed descriptor-specific encoder producing these protobuf bytes. Generic RPC hashing remains protobuf SHA256 with only its key cleared; neither JSON nor `F` is wrapped around its byte input. Profile identity is retained alongside hash evidence; any future wire profile field is hashed normally rather than silently removed.

Strict unknown-field rejection is not ordinary additive-schema compatibility. P1 is a closed fixture schema and cannot govern production generic RPC acceptance until Backend/compatibility owners approve descriptor/profile dispatch and rolling N/N−1/replay behavior. Proposed fixture dispatch selects an explicit `(fully qualified method, profile revision, descriptor hash)` from a fixed accepted catalogue **before request/key/hash parsing**; no inference from payload fields or fallback to a newer descriptor. A production adapter needs an owner-approved, authenticated method/profile dispatch binding before these rules can apply; this draft neither adds a header nor changes Backend's existing generic schema. Never drop unknown fields before computing a generic hash. Keep unchanged historical profiles/decoders available for their eligible replay horizons. A new additive field requires a new accepted profile and explicit compatibility/admission policy; unknown profiles reject, and an original key association cannot migrate to new semantics through profile negotiation. Future vectors must cover a newer optional field during N/N−1 rolling operation, its explicitly approved acceptance/rejection, old/new dispatch, downgrade rejection and historical replay.

| Topic | Exact P1 rule and future validation obligation |
| --- | --- |
| Fields / wire | Encode known fields in ascending numeric tag order recursively, contiguous occurrences for each repeated field. Use shortest legal tag/length/value varints; protobuf wire types follow declared types. Reject unknown fields, groups, wrong wire types, truncated values, overlong/overflow varints, duplicate singular fields and competing oneof cases **before ordinary parsing loses that evidence**. A parsed generated message alone cannot prove absence of duplicate wire occurrences. |
| Presence/defaults | Every singular scalar/string/bytes field is declared `optional`; the catalogue marks mandatory presence and permitted values. Present zero encodes; absent encodes nothing. Missing mandatory presence rejects. Optional absence and present default are distinct. Mandatory nested messages must be present and valid, never an empty-message shortcut. Clearing the generic key means clearing its presence entirely, not assigning an empty present string. |
| Numbers | Numeric fields use only `uint32`, `uint64`, `sint32`, `sint64`; ZigZag for signed coordinates, normal varint for unsigned values. No floats, doubles, numeric enums, booleans, decimal strings, timestamps or duration well-known types in this narrow fixture. Enum-like categories use exact string literals under Backend §2.1; proposed fixture-only literals do not register runtime operations. Checked integer arithmetic; no coercion, wrap, locale conversion or silent narrowing. Domain revisions/quantities/generations use 1…2^63−1 where declared; zero coordinates remain legal. |
| Text / bytes | Strings use valid Unicode scalar sequences encoded as strict shortest UTF-8; reject malformed UTF-8/unpaired surrogates. Preserve exact code points. Registry ID fields additionally pass their owner's grammar and retain original bytes. Raw digest fields are exactly 32 bytes, never hex/base64 strings. No opaque embedded JSON, protobuf `Any`, extensions or untyped geometry blobs. |
| Collections | No maps or repeated scalar fields in P1. Repeated messages representing sets sort by the catalogue's unique key using unsigned byte lexicographic comparison, rejecting duplicate keys even when payloads agree. Ordered sequences, when later approved, preserve order and use a new explicit catalogue entry. Empty repeated fields encode no occurrences. |
| Input vs projection | The generic RPC request must already satisfy its accepted collection order and presence rules; reject a nonconforming wire request rather than silently normalize its fields. Its hash then clears only the key. Semantic projection is separate: a validated domain intent is copied into the exact catalogue and its declared sets sorted before serialization. These rules do not promise arbitrary payloads with different encodings share a generic hash. |

These are deliberate restrictions beyond protobuf's permissive decoder behavior. Field presence and encoding details follow the publisher's [presence guide](https://protobuf.dev/programming-guides/field_presence/) and [wire guide](https://protobuf.dev/programming-guides/encoding/); restricted acceptance and rejection rules are project proposals. Historical requests remain tied to their original descriptor/profile; no silent rehash under a new schema or reuse of retired field tags.

## Bounded initial semantic catalogue

Propose `lsf/construction-intent/nonterrain-fixture/v1`, solely for isolated cross-language identity fixtures. It models placement of one anchored functional-object definition without terrain, excavation, rotated shapes, salvage, repair or fractional ledgers. This does not define the production `CommitConstruction` request or prove those omitted operations safe. Owner approval must confirm applicability before any real object can use it. Authority-only World participation is still required by the authority proposal; absence of terrain does not remove admission fences.

Notation: `tag:name:type`; all singular fields mandatory `optional` presence unless explicitly noted. Strings are nonempty and ≤128 UTF-8 bytes in this fixture; owner-registered IDs additionally obey Registry grammar. Version labels/quote references/zone names use exact owner-defined strings, not newly invented Registry prefixes. `u+` means uint64 1…2^63−1; `digest` means bytes32. Collections below may be empty only where stated. No undeclared field is implied by the catalogue.

| Proposed message | Exact fields and constraints |
| --- | --- |
| `IntentP1` | `1:realm:string`, `2:actor_character_id:string`, `3:claim_id:string`, `4:operation:string` (literal `fixture_place`, proposed solely for this catalogue, not a Registry runtime operation), `5:quote_reference:string`, `6:quote_snapshot_digest:digest`, `7:content_version:string`, `8:config_version:string`, `9:permission_revision:u+`, `10:claim_revision:u+`, `11:world_revision:u+`, `12:placement:PlacementP1`, `13:sources:repeated SourceP1`, `14:beneficiaries:repeated BeneficiaryP1`, `15:participants:repeated ParticipantP1`. Claim uses `clm_`; actor uses `chr_`. Quote snapshot digest references an immutable, owner-validated quote, not a substitute for the enumerated intent fields. |
| `PlacementP1` | `1:zone_id:string`, `2:definition_id:string`, `3:grid_x:sint32`, `4:grid_y:sint32`, `5:grid_z:sint32`, `6:orientation:uint32` (=0), `7:target_revision:u+`. Grid is Construction's 0.5 m integer XYZ; pose is definition's authored orientation only. Definition identity/interpretation is pinned by content version; no unspecified rotation or geometry representation. |
| `SourceP1` | `1:container_id:string` (`ctn_`), `2:slot_index:uint32`, `3:item_instance_id:string` (`itm_`), `4:quantity:u+`, `5:expected_container_revision:u+`, `6:expected_item_revision:u+`, `7:owner_kind:string` (literal `character` or `guild`), `8:owner_id:string` (`chr_`/`gld_`, matching kind). Nonempty list; set key is `F("lsf/source-key/v1", S(container_id), U32BE(slot_index))`. Slot addressing/units remain Inventory-owner approval gates; fixture schema is no implementation claim. |
| `BeneficiaryP1` | `1:owner_kind:string` (literal `character` or `guild`), `2:owner_id:string`; matching `chr_`/`gld_`. Empty only when the quote declares no return/refund beneficiaries. Set key is `F("lsf/beneficiary-key/v1", S(owner_kind), S(owner_id))`. This lists proposed recipients, not authorization or a computed salvage allocation. |
| `ParticipantP1` | `1:service:string`; nonempty list, set key `S(service)`. Names must be accepted service identities; the complete set includes all required admission authorities once owners accept their participation contracts. Do not guess a session/Character service participant or remove an authority to make the fixture pass. |

Semantic bytes `B = P1(IntentP1)`; digest `H = SHA256(F("lsf/construction-intent/nonterrain-fixture/v1", B))`. Domain label is also the profile identity retained with `H`. Excluded: server-issued action ID, original/retry/internal keys, transport correlation/deadline, delivery generation/incarnation, worker identity and admission grant receipts acquired after action allocation. Expected revisions, quote identity/snapshot, exact proposal, fixed participants and pinned content/config/permission evidence remain included. Quote expiration is checked from immutable quote evidence; changing that quote requires a new intentional request after resolving the prior outcome.

Participant prepared/applied, decision and completion digests are **different profiles**, not `H` or the generic RPC hash. Reserve labels `lsf/construction-prepared/v1`, `lsf/construction-applied/v1`, `lsf/construction-decision/v1`, `lsf/construction-completion/v1`; exact typed catalogues remain B-04/B-05 owner work. They must bind action/H, participant and original preparation identity, exact staged/applied deltas/revisions and admission grants; decision binds its immutable prepared set, completion every matching applied digest. A new delivery generation cannot regenerate historical receipts or alter their set. Labels alone do not close certificate byte schemas.

## Future acceptance vectors and gate closure

After B-05 scope approval, author schema/descriptors and positive/negative fixtures in a separately named write set; record literal request bytes, key-cleared bytes, semantic bytes, every framed input, expected raw/hex hashes, scope mapping and expected outcome. Compute reviewed golden values independently in pinned C# and C++ implementations; a second implementation must consume the same fixture data without copying the first encoder. C++ evidence concerns shared contract encoding only, not an assignment to modify E1 Unreal adapters. No digest value is claimed as measured by this document.

| Case group | Required future result |
| --- | --- |
| Stable replay | Same intent/key returns one action; two concurrent identical admissions commit one association; restart and generic-cache expiry resolve that association. Transport-key change leaves `H` stable but does not authorize retry as a new unresolved action. |
| Separation | Different realm/character/family yields a different framed scope; same textual key on separate RPCs retains Backend isolation. Forced test-double boundary/semantic digest collision rejects unequal retained bytes, leaks no result and creates no replacement action. |
| Semantic mutation | Change one source slot/quantity/owner/revision, beneficiary, pose coordinate, quote, permission/config/content version or participant: changed `B/H`; same original key rejects. Reordering a semantic set before projection is equal; duplicate set keys reject; noncanonical RPC list order rejects. |
| Presence / wire | Absent vs present coordinate zero differs or mandatory absence rejects; positive/negative sint32 endpoints agree cross-language. Reject duplicate singular/oneof, unknown field at any depth, map, nonminimal varint, wrong wire type, overflow/truncation, unknown operation and forbidden float field. |
| Text / framing | ASCII and valid non-ASCII quote labels agree byte-for-byte; canonically equivalent Unicode spellings remain different; malformed UTF-8 rejects. Delimiter-containing parts cannot alias framed scopes. Empty/invalid/lowercase ULID and overlength keys reject without trimming. |
| Delivery / evidence | New generation/incarnation changes step key and generic fence-bearing request hash while leaving `H` unchanged. Changed grant receipt affects prepared evidence only. Stale authority rejects; current authority replays the original immutable decision/certificate. |

Gate closure requires accepted initial operation/catalogue, exact Registry/slot/quote/authority bindings, collision/retention strategy, owner-approved wire-validation location, pinned descriptor/compiler/runtime artifacts and independently matching bytes plus rejection results. Until then this is design preparation. Terrain operations remain blocked on DEC-03's exact representation/profile; prepared/applied/certificate schemas remain separately blocked. Passing nonterrain fixtures cannot approve omitted geometry, all construction operations, participant implementation, production durability or mutation enablement.
