## Minimal logical durable records

Concrete DDL and bytes are later S deliverables; this packet defines necessary uniqueness and atomic associations without creating schemas. Every owner keeps its own records; no cross-database joins/transactions. All immutable comparisons include exact profile identities, not digest bytes alone.

| Record / owner | Required key and invariant |
| --- | --- |
| Scoped action association / coordinator | Unique `(realm, actionId)` fixes origin/hash/profile/fixed set; scoped command key uniquely maps to that action and cannot be recycled after cache cleanup. |
| Action authority / coordinator | One `(realm, actionId, origin)` row: admitted delivery incarnation/generation/worker, revision, gate/recovery status, deadline and immutable prepared-set/decision/completion references. Positive int64 generation; checked overflow. |
| Participant / each receiver | Same immutable action key plus unique action-ID association; admitted tuple/enrollment reference, revision and B-04 state. Absent barriers persist EMPTY tombstones. Terminal identity/evidence survives ordinary RPC-cache expiry. |
| Effect/hold and receipts / each owner | Unique `(action identity, participant, effect kind)` with immutable prepared/applied/aborted/completed evidence; exact held synthetic quantity and projection/availability flag. State/effect/receipt commit atomically; no prepared digest is invented on absence. |
| Enrollment gate/mapping / every owner | Unique scope/revision and manifest reference; prior enrollment, pending replacement, approved action-origin mapping and phase permissions. Staging preserves active tuples; gate CAS serializes with phase effects. External proof references are not self-validating assertions. |
| Barrier reconciliation / coordinator | Unique `(action, delivery incarnation, generation, worker, participant)` binds durable ack/evidence; all fixed entries and exact current tuple required for recovery progress. Stale ack cannot satisfy replacement's set. |
| Pending delivery / each owner | Stable unique step/event identity and payload/profile/digest committed with state/effect; attempt/delivery status mutable separately. Sender retry never changes immutable decision/evidence. Receiver verifies before durable replay response. |
| RPC dedup / each owner | Unique `(service, operation, key)` binds full request hash and result atomically with local work; changing delivery changes step key, not semantic identity. Duplicate cache reads still enforce current fencing/enrollment; no stale cached success bypass. |

## Transaction and delivery pseudocode

No interservice request, wait for another vote, external proof call or test scheduler wait may run under an owner row lock. Pause hooks inside locks may signal the harness and use bounded local test gates, without issuing cross-owner calls. Record lock acquisition/commit order explicitly rather than inferring it from RPC completion timestamps.

1. `receive`: validate transport/profile/recipient; call authoritative coordinator lookup outside transaction; verify its issuer and exact action/current state/allowed phase/payload/evidence binding, then retain that verified tuple. S uses explicitly trusted stub inputs; T authenticates the direct Building lookup peer and response association. A lookup timeout/unknown action or phase inconsistent with authoritative state authorizes no mutation or guessed abort.
2. `local transaction`: acquire scope/enrollment gate lock first, then action/participant association (insert-if-absent under unique constraint, re-read winner), then resource rows in stable sorted key order, then local dedup/effect/receipt/pending-delivery rows. Proposed fixture matrix: ordinary phases/barriers take mutually compatible shared/read gate locks; freeze/enrollment transitions require an exclusive conflicting gate lock. Recheck gate atomically under that lock; all writers obey this order and no lookup occurs inside it. Before code, S owners must approve exact PostgreSQL lock modes/conflicts and the planned simultaneous-phase/freeze tests; S closure requires their observed results. This accepts no production optimization. A coarse exclusive-gate alternative is permitted only with explicit serialization-only evidence, without claiming resource-lock-order coverage. An insert race rechecks winning immutable identity. CAS/serialization failure retries original key after rollback; no partial effect escapes.
3. `barrier`: recheck local gate/mapping, verified identity/fixed set and expected revision. Within admitted incarnation reject lower generation or same-generation/different worker; repeated exact tuple returns current durable receipts. Higher generation updates tuple only here. For mapped restore, CAS expected old tuple/reference to new incarnation/generation 1/approved worker, preserving origin/state/evidence/holds. Unknown mapping or ordinary-phase tuple change rejects. Commit tombstone/tuple/ack together, then reply.
4. `phase`: require exact stored tuple, allowed local gate/phase and verified authoritative lookup state/phase/evidence binding. PREPARE requires authoritative undecided state and local EMPTY/exact prepared replay; fresh prepare after authoritative decision rejects even if local state is still EMPTY/PREPARED, and terminal prepare rejects. COMMIT requires exact local prepare and exact lookup-bound durable commit; ABORT requires exact lookup-bound durable abort and never reverses commit. COMPLETE requires exact lookup-bound durable certificate, local applied receipt and all-fixed-applied set. Write synthetic effect/hold/state/receipt/pending work/dedup result together. Reply only after commit; ambiguous reply queries retained state. QUERY reads permitted evidence and cannot authorize creation. A lookup genuinely acquired before a later remote decision remains subject to B-04's receiver-barrier/local-terminal ordering; no global atomic lookup/write claim is made.
5. `takeover`: coordinator locks same gate/action and CASes exact incarnation/generation/worker/revision to generation+1/new worker/recovery pending. Commit before sending barriers. Collect each ack outside locks; local transactions persist acks only if still current. Reconcile original evidence and all fixed exact-tuple barriers before additional prepares/new decisions/completion; old worker CAS fails. Immutable historical decision/completion bytes remain unchanged.
6. `decision/completion`: one coordinator transaction checks current tuple, permitted gate, all prepared or all-applied evidence and required barrier set, then stores immutable decision/certificate with pending deliveries. Deadline abort uses authoritative DB UTC after locking; expired committed work rolls forward. Original snapshot absence cannot establish an undecided frontier. Local geometry participates through the same receipt/barrier checks.
7. `relay/restart`: committed pending rows drive at-least-once delivery outside locks. Lost response, sender crash or relay restart repeats same step/evidence; receiver records once. Acknowledgment updates sender work conditionally. Projection/outputs remain unavailable until exact completion; distinguish committed notification from protocol delivery. No Kafka/publication guarantee follows from a database-backed test relay.
8. `enrollment`: persist freeze gate, approved manifest/proof references and STAGED mapping without switching active tuples; all scoped enrollment acks precede RECONCILING. Only explicitly approved recovery phases can run there. Install mapped barriers and reconstruct trustworthy frontier/receipts; OPEN requires all scoped reconciliation/readiness approvals. An R adapter must independently verify external proof before local CAS; S/T stubs test local gate behavior only.

Test pauses/crashes at: before row lock, after verified lookup, after lock/before CAS, after effect/receipt/pending insert before commit, after commit before reply, after coordinator takeover commit before barrier send, after receiver commit before ack persistence, and after certificate commit before partial release. Kill the owning child/session or sever the registered proxy connection; restart with fresh connections and read durable rows. Distinguish process termination from actual PostgreSQL restart/WAL recovery; test both separately where approved. Keep synchronous durability enabled and record settings; one-machine power-loss/storage guarantees remain unproved.
