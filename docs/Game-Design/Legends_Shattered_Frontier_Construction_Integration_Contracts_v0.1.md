# Legends of the Shattered Frontier — Construction Integration Contracts

Version 0.1 — Designed extensions; not delivered services, RPCs or storage migrations.

## 1. Ownership and compatibility

[Construction](Legends_Shattered_Frontier_Construction_System_Architecture_v0.1.md) owns placement, costs, material sourcing and structural behavior. [Building and Territory](Legends_Shattered_Frontier_Building_and_Territory_System_v1.0.md) owns claims and capabilities. [Itemization](Legends_Shattered_Frontier_Itemization_Architecture_v1.0.md) remains the sole writer of inventory, container rows, item instances, escrow and the hash-chained item ledger. This extension adds construction participants and receipts; it does not permit another service to write inventory tables. [Tuning](Legends_Shattered_Frontier_Tuning_and_Configuration_Architecture_v0.1.md) controls eligible balance settings; transaction guarantees are code invariants.

`building-service` coordinates each `cba_` construction action. The authoritative zone validates live geometry, reach, collision, support and actor state. World owns durable terrain changes. Inventory owns all material reservations, consumption and returns. Each participant keeps its own database transaction; the protocol below supplies one durable outcome across those transactions. There is no cross-service shared database transaction.

## 2. Container extension

Reuse existing `ctn_` identity, character/guild ownership, slot addressing, item revisions and owner-row locking order from Itemization's Item Model part §3/§6. The Shared Registry defines the `construction_cache` and `construction_recovery` container kinds for this extension. The claim points to its controlling character/guild and the cache retains that canonical owner; an account is not a cache owner.

| Field | Required meaning |
| --- | --- |
| `container_id`, `owner_kind`, `owner_id`, `version` | Existing container identity and owner; revision increases on every stock/access-affecting mutation. |
| `structure_id`, `claim_id`, `zone_id` | Attached cache location/authority; recovery storage may retain historical IDs without live geometry. |
| `definition_id`, `content_version` | Shipped capacity, allowed tag and stack policy; not per-instance GM overrides. |
| `automatic_supply_enabled` | Explicit cache setting, initially false; owner enables it after seeing shared-stock implications. |
| `permission_revision`, `lifecycle_revision` | Authority revisions validated and fenced at commit, including claim capture, archive and lock state. |
| `recovery_entitlement` | Controller or explicit siege loot grant; never infer access from proximity or who broke a structure. |

Launch cache definition: 40 slots, maximum 1,000 units per slot bounded further by the item definition, no stationary weight limit, `construction_material` tag only. Each slot holds one compatible definition/quality/provenance/binding lot under Itemization's existing merge rules. Reject bound, quarantined, escrowed and restricted materials. Deposits from another owner use existing escrow and transfer the ordinary unbound stock into controller ownership. Construction sourcing does not itself transfer ownership to the builder. Claim permissions and manual storage access remain independent.

Recovery storage uses the existing system-overflow ownership pattern with a required character/guild beneficiary authority and origin receipt. It is not an accessible unlimited bank: only receipt-generated returns enter it; its beneficiary may withdraw through normal manual-access checks, escrow and inventory capacity rules. Guild recovery requires the guild's manual withdrawal permission. Personal recovery persists until normal account deletion; claim archive alone does not destroy it. Guild dissolution follows Backend's 30-day asset retention and subsequent `guild_dissolution` destruction policy, including applicable legal/enforcement holds. Pending action decisions must resolve before destruction; deletion cannot erase their conservation receipts. No unrelated despawn timer applies. Historical entitlements never assign stock to the last interacting builder.

## 3. Durable action records

These logical records define the required schema semantics. Physical migrations belong to each writer and must be registered before implementation.

| Record / writer | Required fields and constraints |
| --- | --- |
| Action / Building | `action_id:cba_`, actor, claim, action kind, canonical request hash, affected geometry keys and expected revisions, content/config versions, permission revision, deadline, fencing token, participant IDs, durable decision, result receipt. Unique action ID and immutable request hash. |
| Debit allocation / Inventory | Action ID, source container/item/lot, source owner, reserved quantity, input revision, fence, attributed cell/object cost share, refundable classification. Unique allocation key; available stock excludes active holds. |
| Geometry intent / Building or World | Action ID/fence, exact before/after geometry versions, affected region keys, support-validation result and durable staged delta; no success projection before commit. |
| Decision / Building | Exactly one of commit/abort, persisted durably with fence and participant digest. Cannot change after publication. Participants authenticate its source and verify matching action hash. |
| Return entitlement / Inventory | Original debit allocation, triggering destruction/refund action, eligible quantity, recovery fraction, cumulative credited quantity, beneficiary or explicit seizure grant, destination receipt. Uniqueness prevents repeat claims. |
| Participant outbox | Decision application, ledger entries and domain-event publication in each local transaction; replayable until acknowledged. |

Item ledger entries retain source and sink catalog requirements, causation ID and lineage. Construction consumption uses sink `construction_material_consumed`; returns use source `construction_material_return`. Do not disguise building costs as crafting attempts or restore terminal consumed item rows. Returned material is a new lineage-linked lot, credited once with the source code and original debit allocation. Item quality and restrictions cannot improve through the return.

## 4. Commit protocol

1. The zone creates a non-reserving preview with exact costs, source contributions, revisions, beneficiary destinations and effective configuration. One action stays inside one claim and zone. Inventory-first and nearest-cache ordering follow Construction.
2. On acceptance, Building creates the durable action and acquires fences for affected geometry/claim authorization. It revalidates the preview and actor permissions, then requests participant preparation. Inventory locks owner/container rows in its existing ascending order, checks revisions and reserves every selected lot in one local transaction. It never prepares a partial material set. World stages terrain deltas; Building stages structural deltas after zone validation. Staged data and prepare votes must survive process loss.
3. The prepared authorization fence prevents claim transfer, permission revocation, packing or cache destruction from crossing this operation. Such competing actions either complete first, invalidating the preview, or wait for its decision. Geometry reservations fence conflicting edits and movement/occupancy validation for the short commit boundary; clients cannot enter newly occupied geometry while activation is pending. No network wait is held inside a database lock: durable holds and fence records represent the reservation between calls.
4. When all participants are durably prepared, Building persists the commit decision. Otherwise it persists abort. A pre-decision deadline may cause abort; it cannot undo a persisted commit. Participants consume reservations/apply staged deltas on authenticated commit, or release holds on abort, exactly once. Individual participant progress may differ during recovery, but no player-visible success, loot, refund or usable geometry is exposed until all required participants confirm the same outcome.
5. Inventory applies any refund, salvage or terrain-yield credits into action-held output allocations. They remain nontransferable, unavailable to automatic supply, crafting or trade, and excluded from spendable balances until every participant has acknowledged commit. Geometry remains fenced against interaction during this interval. Building then durably marks the action completed, sends an idempotent completion certificate and returns the stable receipt. Participants release output holds and geometry fences only on that certificate. A delayed release may temporarily block availability but cannot expose a credit from an incomplete action. Yield-bearing terrain cells remain fenced until completion, so another action cannot harvest their old state. Disconnection queries the same action ID. Same ID/same hash returns current status or original receipt; same ID/different hash rejects. No caller retries by assigning a new ID to an unresolved action.

If the coordinator fails after commit but before a participant applies it, recovery resends the persisted decision; it never refunds already committed costs on timeout. If a participant is prepared but cannot find a decision, it queries the coordinator's durable store and retains its fence until a definitive result is recovered. No participant independently expires a prepared hold. An unavailable decision store blocks the affected actions and reports recovery pending. Coordinator recovery aborts undecided expired actions using the same decision store; a replacement coordinator uses a newer fence so the old process cannot commit them. Administrative repair follows audited reconciliation and cannot bypass the immutable decision.

Before commit, a validation/authority outage rejects or aborts without material loss. After commit, roll forward to the acknowledged outcome. Permanent restoration from backup must restore the decision log and reconcile participant receipts before reopening affected claims. This contract deliberately trades temporary local unavailability for conservation and coherent construction.

## 5. Permissions and ownership checks

### Participant API extension

These are designed extensions to the owning services, registered with this contract; they are not claims of delivered endpoints. Common fields are action ID/hash, realm, coordinator epoch/fence, authenticated caller and idempotency key. Results include participant revision, immutable prepared/applied digest and status; changing the request under an existing ID rejects.

| Owner / method | Additional request and result contract |
| --- | --- |
| Inventory `PrepareConstructionMaterials` | Exact source lots/quantities/expected revisions, permission assertion, original contribution allocations, proposed held refund/yield lots and destination beneficiaries → durable all-or-none reservation receipt/digest. No client chooses yield or refund quantities. |
| Inventory `ApplyConstructionDecision` | Authenticated immutable coordinator commit/abort and prepared digest → debit/held-credit ledger receipt or released reservations. Commit can never become abort. |
| Inventory `CompleteConstructionMaterials` | Coordinator's durable all-participant completion certificate plus applied receipt → unlock the exact held credits/recovery lots once. A prepared or merely applied decision cannot authorize withdrawal. |
| Inventory `GetConstructionParticipation` | Action ID → prepared/applied/complete state, fence and receipt digests; returns no unrelated stock. |
| World `CommitTerrainEdits` extension | Existing terrain payload plus action ID/epoch, `construction_phase` (`prepare`, `apply`, `activate`, `abort`) and coordinator decision digest. Prepare stages invisible ops; apply records committed heads and holds their active projection; activate requires the completion certificate and permits replication; abort removes only undecided prepared ops. Replaying any phase is idempotent. |

The completion certificate records every required applied participant digest and is written only after they agree; inventory spending and usable terrain require it, not arrival order of independent acknowledgments. Activation delivery can be replayed after a crash. Terrain read requests encountering an applied but not activated head return recovery-pending rather than an incoherent mixture. Building's analogous local geometry/stock-free actions use the same action state machine.

Inventory obtains a server-authenticated authorization assertion tied to actor, action hash, claim, sources, operation, permission revision and fence. A client-supplied permission flag is never evidence. Build and repair require their respective claim capability plus automatic supply access to each selected cache. Manual inspection, deposit, withdrawal, packing and governance are separate checks. A supply-only builder may see required aggregate source amounts without receiving unrelated container contents.

Cache packing requires empty/unreserved stock, manual withdrawal and structure modification rights, no active siege, and destination capacity. Container retirement and placeable restoration share a durable action; the packed item preserves lineage and cannot revive its former contents. Transferring the packed item uses ordinary escrow. Capture changes controlling authority only through Territory's explicit outcome and Inventory escrow/ownership transition; construction permissions never imply ownership transfer.

## 6. Refund and salvage conservation

Every consumed unit is attributed to the built cell/object and its contributing authority. Personal inventory contributions belong to that character; cache contributions belong to the cache controller at debit time, rather than the depositing character or acting builder. Ownership transfers carry an explicit disposition of historical contribution entitlements; absent that disposition they remain with their original beneficiary. An authorized siege capture/loot grant is a separately audited transfer, not a side effect of demolition.

Construction's eligible 60-second Undo/Reclaim returns 100% of the untouched original structural input, attributed to its original contributors. Eligibility and conflict checks follow Construction; after that window or loss of eligibility, voluntary demolition and material replacement recover 50%. Unsupported collapse and authorized combat destruction recover 25%. Uncommitted preview cancellation consumes and returns zero. A committed transaction failure follows §4 and cannot create a second refund. Repair inputs, spent fuel/ammunition, upkeep and already salvaged material generate no new structural refund entitlement. Functional items that pack intact use their packing contract and produce no simultaneous shell salvage.

Compute returns from original debit quantities using fixed rational cost shares, preserving cell attribution across edits, splits and merges. For each contribution and recovery category, credit only `floor(total eligible consumed quantity × recovery fraction) − already credited quantity`; reject negative or repeated entitlement. Recovery fractions and input quantities are those pinned to that geometry generation. Removing one cell extinguishes its entitlement, even when rounding yields zero. A subsequent material replacement starts a new generation with its own real debit. Batch regrouping, repeated partial demolition, material painting and repair cannot round the same contribution upward or count it twice. Sum of credited returns never exceeds eligible debit value or the selected recovery fraction.

Personal shares return to the beneficiary's inventory; shared shares return to the originating cache only if it still has the same controlling authority and accepts the lots. Full, destroyed, locked or transferred destinations route to beneficiary-restricted recovery storage. Automatic-supply permission cannot withdraw that recovery storage. The preview explains this destination; the acting builder cannot redirect shared returns into their own backpack or an unrestricted drop. Siege-entitled salvage uses the explicit loot beneficiary and Territory's access rules. An ordinary collapse does not grant attackers ownership.

Destroying a cache moves each stored lot once into persistent recovery storage with its lineage and applicable loot entitlement. Contents remain distinct from the shell's 25% combat or 50% voluntary salvage. Permission-protected contents never become public because the original container disappeared. Destruction, supply withdrawal, packing and ownership transfer serialize through the same fence/revision checks. Recovery follows §2's account-deletion, guild-dissolution and hold policies.

## 7. Delivery gate

Remote cache supply remains disabled until the owning domains implement these records, durable prepare/decision recovery, semantic authorization, ownership-safe returns and registered names. Required evidence covers simultaneous builders, permission changes, cache destruction, coordinator/participant crash points, replay, mixed ownership, partial salvage rounding, full destinations and capture. These are delivery requirements; no runtime implementation or tests are supplied by this documentation change.

## 8. Building service and domain contracts

The Shared Registry registers `building-service`, package `lsf.building_service.v1`, PostgreSQL schema `building`, realm-column isolation, Backend tier 0. The service owns durable claims (`clm_`), structural assemblies and functional objects (`strc_`), sieges (`sge_`) and action decisions (`cba_`). A structure is an assembly record with addressed voxel members, not one service entity per voxel; disconnected components receive new assembly IDs while retaining cell provenance and refund allocations. Functional objects each have a structure ID. Cell addresses are zone-local integer XYZ on the 0.5 m grid; shapes and authored material IDs carry a content version. Every persisted structure includes zone, `cell_key`, touched `chunk_keys`, owner, claim/parcel, revision, mask/material members or functional definition, condition/combat health, supports and contribution references.

Zone servers own active geometry validation, physics queries, support and replication. The service accepts only commands from the current authenticated zone owner with its ownership epoch; clients cannot call mutation RPCs directly. Inventory and World remain sole writers of their domains. Staged decisions, outboxes and recovery holds survive zone failure. Gameplay never assumes a local mutex or a shared PostgreSQL cluster provides cross-service atomicity.

All mutating requests carry `idempotency_key` (maximum 128 characters), realm, actor, canonical request hash, expected revisions, effective config/content versions and causation. The coordinator issues action IDs before prepare. Repeated keys return the same action, including after the seven-day generic RPC cache expires; compact terminal tombstones remain while their geometry, ledger or archive can reference them. Unknown historical IDs cannot create new mutations. UTC timestamps encode real-time deadlines; durations are integer milliseconds and quantities integer units. Internal client-visible errors expose a stable reason plus an actionable message, never inventory contents without inspection permission.

| Method | Required request / response and behavior |
| --- | --- |
| `EvaluateConstructionPermission` | Actor, claim/parcel or public volume, operation, target bounds, source container IDs and expected revisions → allowed, denial reason, effective named rights, policy/claim/permission revisions and a request-bound authorization digest. Rights include build, repair, terrain, demolish-own/demolish-any, operate/configure device, automatic supply, inspect/deposit/withdraw container and govern. Precedence: immutable protection/phase limits, explicit actor/object deny, scope, then explicit grants. No guild/friend inference. This is a non-reserving preview; prepare acquires the fence and rechecks every relevant revision. |
| `PreviewConstruction` | Action kind, exact voxel/terrain/object proposal, source preference and expected world revision → quote ID, request hash, cost/allocation summary, return beneficiaries, support/budget impacts, versions and expiry at 30 real seconds. No stock or geometry reservation. A changed quote cannot silently charge a different amount. |
| `CommitConstruction` | Quote ID/hash and zone ownership epoch → action ID and `pending`, `completed` or `aborted` receipt. Revalidate reach/line of sight/occupancy/support/budgets/unlocks/claim/source permissions and versions; execute §4. Exhausted quote, insufficient stock or stale input returns a refreshed preview without mutation. |
| `GetConstructionAction` | Authenticated actor or authorized support plus action ID → decision, completion status, receipt and permitted result details. Reconnect resolves this before offering a new submission of the same intent. |
| `ReserveClaim` | Entitlement owner, anchor/parcel volume, exclusions and exact recipe quote → claim/action IDs. Exclusive volume, entitlement, material debit and terrain adoption prepare under one decision; no reservation is visible as a live claim before completion. Conflict rejects without charging. |
| `ChargeClaimMaintenance` | Claim, scheduled UTC interval and pinned cost revision → charged or shortfall receipt. Unique claim/interval; fractional costs carry forward, stock is all-or-none, grace/notice transitions are versioned. Zero upkeep explicitly keeps the claim funded, including its anchor minimum, and cancels unpaid reclamation prospectively; it never invents a payment receipt. |
| `ArchiveAndReleaseClaim` | Claim/parcel revision, archive reason, beneficiary manifest and restoration plan → archive/action receipt. Durable geometry/terrain archive, item recovery, entitlement changes and safe World restoration are participants. Release waits for all acknowledgments. Existing stock moves with lineage and is not credited as newly created salvage. |
| `ResolveSiege` | Siege revision, frozen profile, validated objective result and asset/beneficiary manifest → immutable outcome/transfer action receipt. Inventory changes only explicitly contested stock or loot grants; private parcels retain access until Territory's later archive/relocation transaction. No client can submit its own objective result. |
| `LoadClaimStructures` | Current zone owner and snapshot cursor → revisioned structures, budgets, pending action fences and policy snapshot. Reconcile incomplete decisions before enabling edits or inventory interactions. |

`building` persists claim/parcel reservations, grants, budgets, upkeep accruals, structure members/condition, siege snapshots, action decisions, contribution references, exact fractional repair accrual/paid ceilings, archives, notices and an outbox. Spatial reservations serialize overlapping claim attempts. Changes to permissions, movement occupancy, destructive attacks, source containers and build geometry use the same per-target fences; low-priority pending build work never makes a siege target invulnerable. Undecided work expires after 5 real seconds and aborts through its coordinator; a committed recovery fence is never timed out independently. Battle clocks pause for an operationally blocked contested target until a consistent decision is restored, with both sides notified.

Privacy/realm transfer follow Backend's existing participant interfaces: export a player's grants, contributions and personal archive manifest; on deletion settle pending decisions, archive/release personal land safely, remove grants and route or destroy subject-owned recovery through Inventory's account-erasure policy. Shared guild property survives individual erasure; retained decision/ledger references are pseudonymized under the existing retention/hold policy. Character realm transfer is blocked by live property, unresolved contributions/recovery or pending construction; nothing is silently copied across realms. Guild disband follows Backend's recorded succession/dissolution policy and Territory's archive workflow.

### Durable structure event payloads

Registry envelope and `schema_version = 1`; producer `building-service`, topic `domain.world`, partition key `structure_id`, privacy `p1_pseudonymous`. The zone supplies validated facts; only the durable owner's outbox publishes them after action completion. Event IDs remain stable across retries. Inventory allocations/contents are private ledger details and never broadcast in these events.

| Event | Required payload |
| --- | --- |
| `world.structure.placed` | `action_id`, `structure_id`, `claim_id`, `zone_id`, `cell_key` (uint64 decimal string in JSON), `chunk_keys[]`, owner kind/ID, actor character ID (optional for event/system), structure revision, content/config versions, UTC committed timestamp, geometry delta digest, added cell count, functional definition ID when applicable. One event per affected structure, not per voxel; later additions carry the new revision. |
| `world.structure.destroyed` | Same identity/version/actor/location fields, removed cell count, remaining cell count, reason (`demolition`, `collapse`, `combat`, `archive`), salvage receipt references (possibly empty), optional siege ID, terminal flag. Partial removal advances revision; terminal true retires the assembly/object. Packing uses its move receipt and cannot emit both material salvage and intact-item recovery. |

These events are notifications of completed decisions, not commands to repeat material credits. Consumers deduplicate by event ID and structure revision. Detailed claim/maintenance/siege state uses the service's revisioned snapshots and receipts; no unregistered event name is implied.

## 9. Canonical construction configuration declarations

The Registry adopts these exact keys; schemas, bounds and activation are shipped declarations. Percent fields are integer percentages of Standard. Running consumers retain their last good snapshot during control-plane outages. On boot, LiveOps requires a verified disk snapshot less than 24 hours old; otherwise safe/default values carry critical health and block load-balancer/world-zone admission until a valid snapshot is obtained. Launch defaults never authorize opening a zone without that gate. Scope is a whole realm, never per-account variations of shared physics or obligations. All use existing LiveOps `apply_on = immediate` delivery, then the prospective domain boundary below. Persistent publication uses LiveOps's existing config privileges/approval tiers; a GM capability alone grants no publish right. Economy-class keys require tier 3 in production; gameplay keys tier 2, escalating under LiveOps's >25% change rule. A domain event can use only its approved temporary preset, scope and expiry with GM audit/review; no new LiveOps cohort selector is added.
