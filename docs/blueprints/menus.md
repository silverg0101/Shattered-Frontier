# Blueprint: menus and panels (inventory, build palette, station, market, trade, settings, dialogue board, future menus)

The always-on HUD is [ui-hud.md](ui-hud.md). Everything here is for screens the player opens. Rules are written as steps; follow them literally. Code lives in `GameClient/Source/ShatteredFrontier/Public/Framework/SFHudStyle.h` (namespace `SFHudStyle`): a menu composes these helpers and builds no art or colour of its own. `tools/Check-HudStyle.ps1` fails if it does.

## 0. C++ / Widget Blueprint split (phase 1: shared parts and the HUD; other menus still follow sections 1-5 until migrated)

**Rule.** C++ owns everything except UX: data, state, events, input, network and replication hooks, formatting rules and the style tokens (`SFHudStyle`: kit pieces, margins, colours, fonts). The Widget Blueprint (`WBP_*`) owns layout and look, which the owner arranges in the UMG Designer. No logic in Blueprint graphs beyond visuals (event hooks such as `OnStateChanged` / `OnSelectedChanged`).

- C++ bases: `Public/UI/SFUiWidgets.h` (shared parts) and `SFHudWidgets.h` (HUD). Each `UUserWidget` binds the parts it drives with `meta=(BindWidget)` / `BindWidgetOptional`; a base applies the kit brushes, fonts and colours from `SFHudStyle` at creation (and live in the Designer preview). Style values are `UPROPERTY` defaults (`FSFUiTextStyle`, `FramePiece`/`NormalPiece` kit names, `Kind`), so one `SFHudStyle` change updates every widget. Untick `bApplyKitStyle` on one WBP to style it by hand.
- **Kit v7 parents (stage A).** One parent WBP per element type in `/Game/Frontier/UI/Widgets/Common/`: `WBP_WindowFrame`, `WBP_Button`, `WBP_Tab`/`WBP_TabBar`, `WBP_Stepper`, `WBP_Separator`, `WBP_ItemSlot`, `WBP_ScrollList`, `WBP_SearchField`/`WBP_InputField`, `WBP_Dropdown`, `WBP_GoldDisplay`, `WBP_Toggle`, `WBP_SettingRow`, `WBP_ItemTile`. Every new menu is a `WBP_WindowFrame` instance filled through its NamedSlots; never build another button, tab, slot, scrollbar or separator, change the one parent. List rows (market listing, recipe, ingredient) are `WBP_KitRow`, the one shared row. The market board, trade window, recipes (crafting station), build catalogue, quest journal / board, dialogue, gathering skills, settings, the Esc game menu and the defeated screen are such windows (rows below; the defeated screen is a centred frame over a dim); each is a window of `USFWindowStack` (the station panel opens while the player aims at a station, the build catalogue while build mode is on and Esc then leaves build mode) and all of them show the inventory's item tooltip (`UI/SFItemTooltip.h`, parts `Tooltip`, `TipIcon`, `TipTitle`, `TipRarity`, `TipType`, `TipQuantity`, `TipWeight`, `TipDescription`). **Scale convention:** kit art is 2x and Slate draws Box margins in texture pixels, so kit widgets are authored in art pixels (fonts too) and `WBP_WindowFrame` renders its content in a 0.5 ScaleBox; outside a window wrap a kit part in a 0.5 ScaleBox. **No close buttons:** Esc closes the top window (`USFWindowStack`); Windows line up from the left in opening order; closing one (its hotkey or Esc for the newest) slides the rest left. Hover/selection frames on slots, rows and tiles are `HoverFrame`/`SelectFrame` overlays of `USFSelectableWidget`.
- Assets: `/Game/Frontier/UI/Widgets/Common/` and `/Hud/`. They are seeded by `py -3 tools/Run-InEditor.py tools/ui/create_widgets.py` (first drafts from `Private/UI/SFWidgetAuthoring.cpp`; existing assets are skipped, `--force` rebuilds them and discards the owner's layout). After the first run the `.uasset` files are the source of truth.
- Inventory: `Frontier/UI/Widgets/Inventory/WBP_Inventory` (rough first layout; `ASFPlayerController::ToggleInventoryPanel` (I, `SFUi inventory`) creates it from `USFInventoryWidget::AssetPath`). Open them: Content Browser > `Frontier/UI/Widgets/Hud/WBP_Hud` (the HUD; its children `WBP_PlayerFrame`, `WBP_TargetFrame`, `WBP_HudHotbar`, `WBP_HudMinimap`, `WBP_HudQuestTracker`, `WBP_HudToasts` open on their own) `Frontier/UI/Widgets/Unit/` (the unit frames) and `Frontier/UI/Widgets/Common/` (`WBP_WindowFrame`, `WBP_Button`, `WBP_Tab`, `WBP_TabBar`, `WBP_Stepper`, `WBP_Separator`, `WBP_ItemSlot`, `WBP_ScrollList`, `WBP_SearchField`, `WBP_InputField`, `WBP_Dropdown`, `WBP_GoldDisplay`, plus the HUD parts `WBP_PanelFrame`, `WBP_ButtonPrimary`, `WBP_Slot`, `WBP_ListRow`).

**Player level (badge).** `WBP_Hud.Vitals` shows the Progression character level: `level = level_from_xp(xp_total)`, derived by progression-service, not a skill total (Leveling doc section 1). `USFCharacterSessionComponent` copies `GetCharacterState.level` into `USFGatheringPilotComponent::RestoreLevel` on restore; `CharacterLevel` is owner-replicated (default 1) and `USFHudWidget::SyncLevel` (each tick, pushes only on change) calls `Vitals->SetLevel`. XP grants during a session do not change it yet: no client path consumes the `level` of a progression reply, so the badge updates on the next restore until one does. Targets carry no level: `SetLevel(<=0)` collapses `LevelText` (the target frame passes 0).

**Unit frames.** `USFUnitFrameWidget` (API `SetLevel`, `SetName`, `SetHealth(cur,max)`, `SetStamina(cur,max)`) is one hierarchy for every unit frame. `WBP_UnitFrame` holds the owner's hand-laid layout; the children only set the four `EditDefaultsOnly` part toggles (Class Defaults, category "SF Parts"), applied in `NativeOnInitialized` and `NativePreConstruct` (so the Designer previews them) by collapsing the optional bound widgets:

| Child WBP | `bShowBadge` | `bShowName` | `bShowStamina` | `bShowValues` | Used as |
| --- | --- | --- | --- | --- | --- |
| `WBP_PlayerFrame` | on | off | on | on | `WBP_Hud.Vitals` |
| `WBP_TargetFrame` | on | on | off | on | `WBP_Hud.Target` |
| `WBP_PartyFrame` | on | on | on | off | `PartyList` rows (`AddPartyMember`) |
| `WBP_RaidFrame` | off | on | off | off | `RaidGrid` cells (`AddPartyMember(..., bRaid)`) |

Badge = `BadgeRoot` (else `LevelText`), stamina = `StaminaRow` (else `StaminaBar`), values = `HealthText` and `StaminaText`. A new unit frame kind is a child WBP of `WBP_UnitFrame` with other toggles. There is no party system yet: `PartyList`/`RaidGrid` stay empty and collapsed.

**C++ never overrides Designer styling.** C++ sets data only: text values, bar percent, visibility toggles. Fonts, sizes, colours and layout set in the Designer stay. The one allowed fill is a value left unset: `FSFUiTextStyle::Apply` gives a text block the project font family only while it still has the UMG default (the runtime composite font cannot be picked in the Designer), and sets size and colour only while they equal the UMG defaults; a bar image with no material gets the kit's `MI_UI_BarFill_*`. Never call `SetFont`, `SetColorAndOpacity`, `SetJustification` or padding on a Designer-owned widget from C++ (runtime state tints via `SetTint` are data).

Fed by C++: `ASFPlayerController` creates `WBP_Hud` (`USFHudWidget::AssetPath`) and pushes the hotbar from the pilot inventory; `USFE1VitalsHudSubsystem` pushes vitals; `USFQuestPilotSubsystem` pushes quests (`PresentQuests`); `USFGatheringHud` pushes skill toasts (`PushToast`). Still code-built (later phases): prompt bar and the target hit message (`SFHudLayout`), gathering ring (`SFGatheringHud`) and the defeated window (`SFE1VitalsHud`); the market board, trade, recipes and build catalogue are WBP windows (rows above), the other menus below are still code-built.

## 2. Acceptance (pixel-perfect within reason)

At 1920x1080 against the concept: geometry +-2 px (position, size, spacing, padding); type same family and weight, cap height +-1 px, same alignment, nothing truncated; colour dE2000 <= 3 at the sample points; art matches at 1:1 crop (brass hairline, chamfer, nine-slice corners; textures imported at 1x, no mips, `TC_EDITOR_ICON`); states match the concept or section 1. Measured by `py -3 tools/ui_pixel_diff.py --all`; judged by a fresh Fable reviewer using those numbers ([visual-review.md](../visual-review.md)). Where two concepts disagree, section 1 picks the canonical style and the report flags it.

Save as `docs/Game-Design/concept-art/UI/v5/<name>.png`.
2. **Element list.** Create `docs/evidence/ui-v5/elements/<name>.json`: `{"concept": "<name>.png", "elements": [{"name": "...", "rect": [x, y, w, h], "samples": [[x, y, "fill"]]}]}`. 3. **Widget.** `Public/<Area>/SF<Name>.h` + `Private/<Area>/SF<Name>.cpp`, class `USF<Name>` (`UUserWidget`), built in `NativeOnInitialized` with `WidgetTree`; `using namespace SFHudStyle`. ## 5. Known failures (never X, always Y)

1. Never gate the kit load on `GIsRunning`; always `!IsRunningCommandlet()` (`SFHudKit.cpp`). A widget built during the startup map load otherwise gets no kit.
2. Never let `KitImage` draw an empty `UImage` for a missing piece (white square); the helper collapses it.
3. Never write a unicode character as `00B7` in `TEXT()`; always `·`.
4. Never rely on `USizeBox` width to cap a widget in a Fill slot; always `HAlign_Left` on the slot.
5. Never use `UUniformGridPanel` when rows differ (it sizes all cells to the tallest); always one `UHorizontalBox` per row in a `UVerticalBox`.
6. Never let a panel's content exceed its frame; always sum the heights, and `SetClipping(ClipToBounds)` on the frame.
