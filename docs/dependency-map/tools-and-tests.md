## Runtime and data flow

`tools/Build-PlayableServiceRelease.ps1 -OutputDirectory <new-directory-outside-checkout>` builds from an isolated tracked Git archive of the clean committed revision, publishing both managed hosts, owner migration tool, matching content/base schemas and hash manifest with pinned SDK/locked packages. The source snapshot defaults to a sibling `<output>.source`; optional `-SnapshotDirectory` must also be new and disjoint from output/checkout. Ignored files never enter source or release. `py -3 tests/test_playable_service_release.py` covers an ignored content/source sentinel, root SDK/lock/proto closure, Linux manifest lines and seven overlap refusals without SDK/Docker. `ops/steam-server/Services.Dockerfile` builds the immutable service image. `tools/Deploy-Lan.ps1` is the one-command LAN deploy/rollback (host logic in `ops/steam-server/deploy-lan.sh`, which has a `--dry-run`); see `ops/steam-server/playable-release.md`. A deploy does not establish remote gameplay acceptance.

That export also hashes the runnable profile generator and fixed guarded development entrypoint under `Runtime/`. `py -3 tests/test_playable_runtime.py` checks strict profile/resource/project/exposure admission, private authority separation and exact LAN UDP launch. `python3 Runtime/playable-runtime.py profile.json prepare|check|init|start|verify|stop|cleanup` owns only the declared distinct project; cleanup is restricted to an unpublished services-check project. Real isolated PostgreSQL/host/role/restart evidence is required in addition to these tests. The source game Dockerfile installs both the preserved E1 entrypoint and the separately selected Silverbrook services entrypoint; game packaging still requires the integration freeze/UE slot.

`tools/Test-E1Remote.ps1` checks two concurrent client welcomes (Launcher editor or direct packaged -ClientExecutable), fails on explicit network errors, monitors a typed3-120s hold (default3), and cleans only its clients; it does not start/stop that server. Linux hosting setup: `tools/Provision-SteamServer.sh` allocates/mounts the new dedicated LV only on the authorized host. `ops/steam-server/` owns the non-root Docker image, bounded profile validator and Compose runtime; see [runtime instructions](../ops/steam-server/README.md). `tests/test_steam_server_profile.py` checks deployment identity, exposure and resource bounds with `python tests/test_steam_server_profile.py`. Source-engine/cross-SDK setup is tracked in [the Linux build route](e1-linux-server-build.md). `.gitattributes` preserves LF for Linux deployment files; generated IDE configuration and cook file-order logs are ignored.

Native Linux packaging and diagnostics: `tools/Export-NativeLinuxInputs.py` exports unchanged complete Linux Server (default) or diagnostic Client receipt closures and matching portable cook (`--target Server|Client`) with a hash manifest (`--self-test` checks synthetic safety/determinism); `tools/Prepare-NativeLinuxBuild.sh` validates the dedicated LV and separate build identity; `ops/steam-server/NativeBuild.Dockerfile` supplies a non-root native tool environment; `ops/steam-server/run-native-job.sh` serializes bounded setup/UAT jobs, including separate loose `client-stage`. `ClientTest.Dockerfile` and `client-test-entrypoint.sh` define the non-root headless Driver/Observer diagnostic client restricted to the isolated loopback endpoint; they are not a product-client distribution. `run-client-diagnostic.sh` collects finite three-container logs in a separate network namespace with resource/time limits and owned-container cleanup; collection alone does not accept gameplay. Its optional exact `--capture-elapsed-trace` records fixed engine CPU/frame trace channels into the private Server bind; offline Insights analysis is required and elapsed scopes are not scheduled CPU time. Their commands and source/cook provenance are tracked in `docs/e1-linux-server-build.md`; LinuxServer content cooks; the packaged build needs Linux gRPC libraries first (`tools/build-grpc-linux.sh`). No Windows security policy or installed-engine support metadata is changed.

```text
package.json (Node >=24; start/test scripts)
  └─ server/index.js (HTTP, cookie sessions, SQLite persistence, SSE, static files)
       ├─ server/world.js (world creation, players, game actions)
       ├─ data/world.sqlite (snapshot + sessions; ignored by Git; WORLD_DB overrides)
       └─ public/{index.html,app.js,style.css}
             index.html loads app.js and style.css
             app.js → /api/*; canvas/UI ← SSE /api/events
```

`server/index.js` restores/saves the world snapshot and session tokens in SQLite, serves the public assets, and broadcasts state changes. `server/world.js` owns game rules and world state. The browser client sends actions and renders shared state; HTML defines UI elements and CSS styles them. Keep local database files under `data/`; `data/*.sqlite*` is ignored.
