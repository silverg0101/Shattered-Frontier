# Dependency map

## Runtime and data flow

`tools/Test-E1Remote.ps1` checks two concurrent client welcomes (Launcher editor or direct packaged -ClientExecutable), fails on explicit network errors, monitors a typed3-120s hold (default3), and cleans only its clients; it does not start/stop that server. Linux hosting setup: `tools/Provision-SteamServer.sh` allocates/mounts the new dedicated LV only on the authorized host. `ops/steam-server/` owns the non-root Docker image, bounded profile validator and Compose runtime; see [runtime instructions](../ops/steam-server/README.md). `tests/test_steam_server_profile.py` checks deployment identity, exposure and resource bounds with `python tests/test_steam_server_profile.py`. Source-engine/cross-SDK setup is tracked in [the Linux build route](e1-linux-server-build.md). `.gitattributes` preserves LF for Linux deployment files; generated IDE configuration and cook file-order logs are ignored.

Native Linux packaging and diagnostics: `tools/Export-NativeLinuxInputs.py` exports unchanged complete Linux Server (default) or diagnostic Client receipt closures and matching portable cook (`--target Server|Client`) with a hash manifest (`--self-test` checks synthetic safety/determinism); `tools/Prepare-NativeLinuxBuild.sh` validates the dedicated LV and separate build identity; `ops/steam-server/NativeBuild.Dockerfile` supplies a non-root native tool environment; `ops/steam-server/run-native-job.sh` serializes bounded setup/UAT jobs, including separate loose `client-stage`. `ClientTest.Dockerfile` and `client-test-entrypoint.sh` define the non-root headless Driver/Observer diagnostic client restricted to the isolated loopback endpoint; they are not a product-client distribution. `run-client-diagnostic.sh` collects finite three-container logs in a separate network namespace with resource/time limits and owned-container cleanup; collection alone does not accept gameplay. Its optional exact `--capture-elapsed-trace` records fixed engine CPU/frame trace channels into the private Server bind; offline Insights analysis is required and elapsed scopes are not scheduled CPU time. Their commands and source/cook provenance are tracked in `docs/e1-linux-server-build.md`. No Windows security policy or installed-engine support metadata is changed.

Optional art prototype: `GameClient/ArtSource/GreenlandsWaystone/` holds the concept-derived turnaround, editable Blender source, FBX/GLB, preview and provenance manifest. `tools/Create-E1Waystone.py` regenerates geometry/exports into a new folder with Blender5.2.2; see its README for the exact command and limitations. It does not import into Unreal or change map/collision. Existing reference artwork is `docs/Game-Design/concept-art/`.

Reusable art prompts: [concept-art template library](art-templates/README.md) provides mostly filled mount, creature, weapon, armor, building, prop and terrain prompts for Blender visual references. Fill only the main concept; optional existing artwork supplies style cues. These generate reference images, not production meshes or gameplay configuration. [Image-to-model session guide](art-templates/generate-model.md) routes an image to editable Blender source, exports, previews and provenance with explicit prototype limitations and visual/reimport checks.

E1 Unreal implementation now lives in `GameClient/ShatteredFrontier.uproject` (UE 5.8.3). `Source/ShatteredFrontier{,Editor,Client,Server}.Target.cs` share the `ShatteredFrontier` module. Its Framework GameMode owns server spawn/possession; Characters uses standard replicated CharacterMovement. `SFE1Settings` and `Config/DefaultGame.ini` define bounded release-only fixture values. `DefaultEngine.ini` selects `/Game/Frontier/Maps/Greenlands_E1`; `DefaultGame.ini` also owns packaging `MapsToCook`; `tools/Create-E1Map.py` creates the graybox map through editor-only Python/EditorScriptingUtilities and refuses overwrite. `tools/Test-E1Connections.ps1` launches a loopback editor server/two hidden clients, checks welcome/distinct possession logs and stops its own processes. See [GameClient startup/settings](../GameClient/README.md), [E1 evidence](evidence/e1-foundation.md), and [Linux server prerequisites](e1-linux-server-build.md). `tools/Build-LinuxServer.ps1` validates a pinned source engine/SDK and invokes Linux x86_64 server UAT packaging into ignored `Artifacts/`; it does not deploy. Launcher editor build success does not establish packaged Server support.

E1 validation: `Interaction/SFE1PlayerController` owns target/revision intent and server checks; `SFE1InteractionTarget` is a replicated non-economic probe. `Private/Tests/SFE1{Interaction,Movement}Tests.cpp` are editor-only focused automation. `Tests/SFE1NetworkScenario` is an explicitly enabled finite development harness using normal owning-client input and replicated PlayerId correlation. `tools/Test-E1Lifecycle.ps1` verifies departing cleanup/surviving possessions; `tools/Test-E1NetworkScenario.ps1` verifies movement/probe with actual Normal/Adverse100 packet settings, optional720p/1080p offscreen frames or rendering without screenshots, opt-in local pawn-cache substitution with authoritative denial/stationarity checks, and flush-verified10s CSV profiles/actor snapshots. Frame intervals include waits and are not simulation CPU/capacity acceptance. See `GameClient/README.md` and the foundation evidence for commands/limits. Legacy input is explicit; editor EnhancedInput auto-upgrade is disabled.

```text
package.json (Node >=24; start/test scripts)
  └─ server/index.js (HTTP, cookie sessions, SQLite persistence, SSE, static files)
       ├─ server/world.js (world creation, players, game actions)
       ├─ data/world.sqlite (snapshot + sessions; ignored by Git; WORLD_DB overrides)
       └─ public/{index.html,app.js,style.css}
             index.html loads app.js and style.css
             app.js → /api/*; canvas/UI ← SSE /api/events
```

`server/index.js` restores/saves the world snapshot and session tokens in SQLite, serves the public assets, and broadcasts state changes. `server/world.js` owns game rules and world state. The browser client sends actions and renders shared state; HTML defines UI elements and CSS styles them. Keep local database files under `data/`; `data/*.sqlite*` is ignored.

## Routes and commands

| Method / path | Purpose |
| --- | --- |
| GET `/`, `/app.js`, `/style.css` | Serve browser client assets |
| GET `/api/me` | Return current player or 401 |
| POST `/api/join` | Create player/session; set `frontier` cookie |
| GET `/api/events` | Authenticated Server-Sent Events state stream |
| POST `/api/action` | Apply authenticated game action |

Run `npm start` to start the local server (`PORT`, default 3000; binds 127.0.0.1). `npm test` runs the full suite and requires an explicit user request. Runtime requires Node 24 or later.

Tests: `tests/world.test.js` imports `server/world.js` for rule validation; `tests/server.test.js` spawns `server/index.js` with a temporary SQLite database for HTTP, SSE, sessions, and restart persistence. Select only tests covering the change with `node --test --test-name-pattern="<matching name>" tests/<name>.test.js`; run a whole file only when all its tests are relevant. Vision: `concept.md`; scope and milestones: `docs/alpha-plan.md`; setup: `README.md`.
