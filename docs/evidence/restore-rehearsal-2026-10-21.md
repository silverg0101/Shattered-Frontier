# Four-store restore rehearsal — 2026-10-21

`tools/Test-RestoreRehearsal.ps1 -EvidenceRoot Artifacts/Persistence/RestoreRehearsal/codex-20261021-i` passed with the pinned .NET 10.0.402 SDK and PostgreSQL 18.6. `harness.json` reports `pass` and `privateStorageRemoved: true`. The owned source and restore clusters used loopback listeners and synthetic credentials; no service outside the fixture was stopped.

The session exercised two characters' trade and listing purchase alongside harvest, craft, housing placement/removal, quest completion and reward. Existing host fault hooks stopped the host after placement intent, refund grant, quest grant, listing escrow, and exchange item delivery. The fixture also used `pg_ctl stop -m immediate`, restarted PostgreSQL, and waited for one listing and one sale to reconcile. Wire replay and outage checks passed. Twelve selected client-acknowledged operation/store keys were checked against durable receipts after recovery and again after restore. Legitimate fan-out was checked explicitly: a harvest ID has progression and quest rows, and a trade offer has its operation and settlement rows. The check does not log every response from the existing wire-test clients, so it does **not** prove zero loss for every acknowledgment in the whole session.

After quiescing the host, one `pg_dump -Fc` captured inventory, character state, housing and exchange schemas in a single PostgreSQL snapshot. Source table counts and sorted-row MD5 digests matched before and after dump. A later trusted wallet credit changed the source. The dump SHA256 was checked, then restored into a second fresh owned cluster; all 20 table counts and digests matched the backup point, and the selected receipts were present. Basic inventory, wallet, housing debit and sold-listing relationships were checked before backup. Each restored store accepted its current schema marker and refused the next version through its adapter (inventory 1→2, character state 2→3, housing 4→5, exchange 3→4).

The shared `Backup-ServiceStore.ps1` / `Restore-ServiceStore.ps1` helpers remain single-store tools. Their Housing path expects schema v3 while Gameplay.Host runs the v4 gameplay migration, so this rehearsal uses one direct four-schema dump and restore. It does not establish production backup scheduling, retention, recovery time, authenticated manifests, or a complete client receipt log.
