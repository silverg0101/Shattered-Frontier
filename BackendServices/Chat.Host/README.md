# Chat contacts service

`Chat.Host` is a loopback gRPC service for directed friend and block contacts and a loopback WebSocket relay for party and whisper delivery. Install the chat schema and `Schema.Erasure.sql` with `SchemaMigration.Tool chat` under `chat_owner`, then grant the runtime role `USAGE` on `chat` and DML on its tables only. Start contacts with `CHAT_HOST_PORT`, `CHAT_CONNECTION`, `SF_CHAT_TOKEN`, `SF_CHAT_PRIVACY_TOKEN`, `CHAT_IDENTITY_URL`, `CHAT_IDENTITY_SERVER_ID`, and `SF_IDENTITY_CHAT_VERIFIER_KEY`. For the WebSocket listener also set `CHAT_WS_PORT` to a separate port, `CHAT_GROUP_URL` to the trusted Gameplay.Host gRPC address, and `SF_GAMEPLAY_TOKEN` to its service credential. The gateway must route `/v1/chat` to the WebSocket listener over a trusted connection. Keep service secrets on trusted hosts.

For add, remove, list, and whisper checks, a trusted caller supplies its service token plus `x-contact-ticket` from IdentityGateway's authenticated `/v1/characters/{characterId}/contacts-ticket`. Chat.Host consumes that short-lived, one-time ticket through `/v1/chat/verify-ticket` and rejects a request whose `character_id` differs from the ticket actor. World-entry tickets have a separate server scope. `IsBlocked` is service-only. `CheckWhisperDelivery` is the server-side policy check: either block direction denies a whisper; friendship is directed and never required for delivery.

The WebSocket client obtains the same character-scoped contact ticket, connects to gateway `/v1/chat`, then sends `{"type":"auth","ticket":"..."}` as its first text frame. An invalid, expired, or replayed ticket closes the socket; success returns `{"type":"status","status":"authenticated"}`. Send `{"type":"send","channel":"whisper","target":"chr_...","body":"..."}` or `{"type":"send","channel":"party","body":"..."}`. Delivery frames are `{"type":"message","channel":"...","from":"chr_...","body":"..."}`; other outcomes use `{"type":"status","status":"sent|invalid|rate_limited|unavailable"}`. Blocked whispers are silently dropped. Party membership is fetched from group-service for sender and recipients on each send; stale connected recipients are not enough to receive. Reconnecting replaces the earlier connection for that character. The launch chat rate is five messages per character with one token restored every two seconds. The 64 KiB frame ceiling is a transport safety bound, not an approved chat body size. The owner still needs to decide a body limit and the safe bounds/effective-time rules for `tune.security.chat_rate` before exposing it in configuration. This relay is process-local; cross-host fan-out and encrypted 30-day message persistence are subsequent integration work. Zone chat is out of scope.

`AddContact` and `RemoveContact` require an idempotency key, return whether the original operation changed a row, and reject key reuse with changed input. `ListContacts` returns only outgoing edges. `EraseContacts` requires the separate privacy token, removes incoming and outgoing edges for the supplied subject character IDs, and leaves tombstones so contacts cannot be recreated after erasure. The privacy workflow supplies the subject's character IDs; it does not write the chat database directly.

Focused check: `pwsh tools/Test-ChatContacts.ps1 -EvidenceRoot Artifacts/Persistence/ChatContacts/<fresh-child>` uses the pinned SDK and owned PostgreSQL instance, checks real IdentityGateway tickets, contacts, whisper policy, privacy erasure, DML-only runtime role, and host restart. It stops all processes it starts.

Transport checks: pinned SDK `dotnet run --project BackendServices/Chat.Host.Tests --configuration Release -- transport` checks auth rejection, blocked whisper, party audience, and reconnect without starting external services.
