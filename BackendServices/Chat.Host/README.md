# Chat contacts service

Text mail uses `chat.mail_messages` from `Schema.Mail.sql`. With `CHAT_WS_PORT` enabled, `POST /v1/mail`, `GET /v1/mail`, `GET /v1/mail/{mailId}` and `DELETE /v1/mail/{mailId}` run on that HTTP/1 listener. Every call consumes a fresh `X-Contact-Ticket` from the actor's IdentityGateway session; POST and DELETE also take `Idempotency-Key`. POST accepts `recipient_character_id`, `subject` (1–256 UTF-8 bytes) and `body` (1–4096 UTF-8 bytes), and returns `mail_id`. Inbox returns encrypted-at-rest subjects; read marks the row read and decrypts the body; delete clears ciphertext. The sender label becomes `erased` after key erasure is scheduled. IdentityGateway's internal character lookup and purpose-scoped data-key API require matching `Identity__DataKeyChatKey` / `SF_IDENTITY_DATA_KEY_CHAT_KEY`. Mail cannot start with `CHAT_WS_PORT` without that key. The shipped `MailControls` record declares 100 messages, 20 sends/hour, 30 seconds between sends, and 30 days expiry, with safe bounds; shared tuning publication remains pending. Item and gold attachments require InventoryLedger mail escrow and are outside this text-only route. Focused checks run with `tools/Test-ChatContacts.ps1` (38 contacts plus 21 mail checks).

`Chat.Host` is a loopback gRPC service for directed friend and block contacts and a loopback WebSocket relay for party, guild and whisper delivery. Install the chat schema and `Schema.Erasure.sql` with `SchemaMigration.Tool chat` under `chat_owner`, then grant the runtime role `USAGE` on `chat` and DML on its tables only. Start contacts with `CHAT_HOST_PORT`, `CHAT_CONNECTION`, `SF_CHAT_TOKEN`, `SF_CHAT_PRIVACY_TOKEN`, `CHAT_IDENTITY_URL`, `CHAT_IDENTITY_SERVER_ID`, and `SF_IDENTITY_CHAT_VERIFIER_KEY`. For the WebSocket listener also set `CHAT_WS_PORT` to a separate port, `CHAT_GROUP_URL` to the trusted Gameplay.Host gRPC address, `SF_GAMEPLAY_TOKEN` to its service credential, `CHAT_GUILD_URL` to the trusted Guild.Host HTTP address, and `SF_GUILD_TOKEN` to its service credential. The gateway must route `/v1/chat` to the WebSocket listener over a trusted connection. Keep service secrets on trusted hosts.

For add, remove, list, and whisper checks, a trusted caller supplies its service token plus `x-contact-ticket` from IdentityGateway's authenticated `/v1/characters/{characterId}/contacts-ticket`. Chat.Host consumes that short-lived, one-time ticket through `/v1/chat/verify-ticket` and rejects a request whose `character_id` differs from the ticket actor. World-entry tickets have a separate server scope. `IsBlocked` is service-only. `CheckWhisperDelivery` is the server-side policy check: either block direction denies a whisper; friendship is directed and never required for delivery.

The WebSocket client obtains the same character-scoped contact ticket, connects to gateway `/v1/chat`, then sends `{"type":"auth","ticket":"..."}` as its first text frame. An invalid, expired, or replayed ticket closes the socket; success returns `{"type":"status","status":"authenticated"}`. Send `{"type":"send","channel":"whisper","target":"chr_...","body":"..."}` or `{"type":"send","channel":"party","body":"..."}`. Delivery frames are `{"type":"message","channel":"...","from":"chr_...","body":"..."}`; other outcomes use `{"type":"status","status":"sent|invalid|rate_limited|unavailable|not_delivered|not_in_party"}`. Bilateral blocks return the generic `not_delivered` status without disclosing a block; non-member party sends return `not_in_party`. Party membership is fetched from group-service for party sender and recipients, or Guild.Host for guild sender and recipients, on each send; stale connected recipients are not enough to receive. Reconnecting replaces the earlier connection for that character. The launch chat rate is five messages per character with one token restored every two seconds. The 64 KiB frame ceiling is a transport safety bound, not an approved chat body size. The owner still needs to decide the player-facing block wording, a body limit and the safe bounds/effective-time rules for `tune.security.chat_rate` before exposing it in configuration. This relay is process-local; cross-host fan-out and encrypted 30-day message persistence are subsequent integration work. Zone chat is out of scope.

`AddContact` and `RemoveContact` require an idempotency key, return whether the original operation changed a row, and reject key reuse with changed input. `ListContacts` returns only outgoing edges. `EraseContacts` requires the separate privacy token, removes incoming and outgoing edges for the supplied subject character IDs, and leaves tombstones so contacts cannot be recreated after erasure. The privacy workflow supplies the subject's character IDs; it does not write the chat database directly.

Focused check: `pwsh tools/Test-ChatContacts.ps1 -EvidenceRoot Artifacts/Persistence/ChatContacts/<fresh-child>` uses the pinned SDK and owned PostgreSQL instance, checks real IdentityGateway tickets, contacts, whisper policy, privacy erasure, DML-only runtime role, and host restart. It stops all processes it starts.

Transport checks: pinned SDK `dotnet run --project BackendServices/Chat.Host.Tests --configuration Release -- transport` checks auth rejection, generic blocked-whisper non-delivery, non-member party and guild rejection, party and guild audience, and reconnect without starting external services. `pwsh tools/Test-ChatUnrealRelay.ps1` builds the fixture and runs two separate Unreal clients through the production transport with fixed development actors and party policy.
