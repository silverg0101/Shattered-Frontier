# PostgreSQL character state store

`PostgresCharacterStateStore` commits accepted Progression skill/XP snapshots and QuestContent step snapshots with source receipts, reward grant intents (destination backpack, quest content revision, expanded item lines, Pending/Complete state and creation time), and compare-and-set revisions. Writes take a transaction-scoped advisory lock derived from the character ID; reads use MVCC without advisory locks. Replay uses the indexed `(domain, character_id, operation_id)` receipt primary key, verifies the original payload digest, and returns the committed result before checking the caller's old revision. Reusing an operation ID with different evidence is rejected. The gameplay host resolves these intents against durable InventoryLedger Grant receipts; this store marks an intent Complete after the matching receipt is checked.

Install `Schema.sql` with a migration identity. For an existing version 1 database with no reward intents, apply `Schema.RewardSnapshot.sql` after any required `Schema.Reward.sql` migration. The snapshot migration rejects existing intents because their historical item lines cannot be inferred from current content. Runtime needs schema usage, data table DML, and marker SELECT. Apply Schema.Position.sql after version 2; it creates position compare-and-set storage and advances the marker to version 3. Each transaction checks schema version 3, migration identity and compatible build range. Missing, inaccessible, unknown, and newer markers fail closed. Connection failures are retryable with the same operation ID; SQL classes 22 and 23 and stale revisions are non-retryable. Success follows commit. The caller supplies trusted evidence, character identity and expected revision; there is no authentication or network adapter.

The Progression snapshot includes effective bounded `ProgressionSettings` and rolling practice/fatigue state across restarts. New characters use the caller's published settings. Quest content revision is pinned at acceptance; content changes require a versioned migration. This project adds no tuning keys. Receipts are retained indefinitely in this MVP; retention and partitioning need later design.

Run `& tools/Test-CharacterStateDurable.ps1 -EvidenceRoot "$PWD/Artifacts/Persistence/CharacterStateDurable/review-01"` with a fresh child path. The owned synthetic fixture uses pinned .NET 10.0.402 and Npgsql 10.0.3, per-run loopback credentials in the child environment, PostgreSQL fsync and synchronous commit, immediate-stop recovery, replay, concurrency, outage/recovery, SQL class 22 and newer-schema checks. It removes only its owned private cluster. This proves a single local database path, not production migration, cross-service reward delivery, backup/restore or availability.

Follow-up verification: gameplay host snapshot recovery passes with changed quest content. The character durable fixture covers version 3 backup and position restore, plus concurrent writes to different characters. No new migration is needed because source receipt lookups already use the existing primary-key index.
# CRF-01 recipe knowledge

Apply `Schema.Recipes.sql` after `Schema.Position.sql` to reach version 4. The progression JSON snapshot now carries `KnownRecipes` with recipe id, source and timestamp. `recipe_intents` records trainer/scroll/discovery decisions under the character lock before an external debit or consume; `CompleteRecipeLearn` updates the progression revision and marks the intent complete in one transaction. The Gameplay.Host sweep retries pending intents after a crash. Backup and restore include the new table and require schema version 4.
