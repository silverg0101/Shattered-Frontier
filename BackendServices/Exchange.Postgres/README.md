# PostgreSQL Exchange store

`PostgresExchangeStore` persists gold wallets, gap-free wallet entries, operation receipts, expiring listings, and trade or listing settlements. The installed schema marker is version 3; every call checks it. A transaction advisory lock serializes decisions across workers; listing commit advances its current revision atomically. SQL classes 22 and 23 reject without retry; storage failures fail closed. Use the existing pinned Npgsql 10.0.3 package.

The caller authenticates character and inventory ownership and validates listing eligibility with the Exchange domain rules. Trade item escrow is funded before settlement begins; listing intents are recorded before their escrow transfer. `CreateListing` stores the seller return container and computes `expires_at` from `ExchangeSettings`' typed listing duration (48 hours by default; 12, 24 or 48 hours allowed; `economy.tuning.publish`; effective for new listings). `BeginTrade` accepts both parties' gold offers and nets them to one payer and payee; equal offers or item-only trades move no gold. `BeginPurchase` reserves the exact spend after checking payee headroom. The coordinator delivers the stored `EscrowDelivery` batch through InventoryLedger with `operationId + "/settle"`, then calls `Reconcile`. It may re-read container revisions before delivery. The operation ID and exact item changes fence the receipt; receipt revisions can advance between Begin and delivery. After a crash, fence the worker before reconciliation. Recovery reads the durable ledger receipt in one ledger transaction. If absent, it writes a zero-change tombstone at the same operation key; ledger fingerprint checks then reject late delivery. Compensation releases the reservation. Inventory outages leave settlement pending; ledger rejection is non-retryable. An active listing remains reserved while settlement is pending.

`CancelListing` and `ExpireListings(now)` return escrow to the saved seller container under a durable ledger return key, then advance the active listing state once. `CancelTrade` fences its pending delivery key, returns the caller-supplied escrow batch, and releases a pending gold reservation once. All three replay their operation receipts; sold listings and committed trades reject cancellation. The coordinator must supply authenticated party/ownership checks and must retry the same operation ID after an interruption. The expiration sweep uses `expire/<listing id>` as its stable key. Listing and transaction fees come from one bounded `ExchangeSettings` snapshot; expiry currently returns escrow without a new fee.

This is a storage and coordination boundary, not an authenticated network API. Production worker fencing, trade escrow funding orchestration, and a shared configuration publisher remain integration work. Gameplay.Host schedules listing and settlement recovery under its advisory sweep lock. The global advisory lock serializes all exchange writes; partitioning it requires durable per-subject worker fencing. Backup and restore support is a later task. The fixture grants the Exchange service role SELECT only on its schema marker and no DELETE on Exchange tables. InventoryLedger uses a separate fixture credential because its current save path needs DELETE and its schema check needs UPDATE.

Run `tools/Test-ExchangeDurable.ps1 -EvidenceRoot <fresh Artifacts/Persistence/ExchangeDurable child>` from the repository root.

Gameplay listing creation records a pending intent in the Exchange operation row before transferring inventory under <operation>/escrow. The intent reserves the listing fee, stores the item, container, price, and duration snapshot, and is resolved by the host sweeper after the recovery window. A confirmed transfer creates one active listing and charges the fee; an absent transfer gets a ledger tombstone at the escrow key and releases the fee hold. A late transfer then fails its operation fingerprint check. The existing schema version 3 operation and receipt columns carry this additive coordinator state; no new package or operator timing override is needed.
