# Gameplay gRPC host (INT-04 preparation)

One ASP.NET Core HTTP/2 process serves five versioned protobuf services: Rewards, Progression (including quest evidence), Housing, Crafting, and Exchange. It binds only `127.0.0.1:$GAMEPLAY_HOST_PORT`. Every RPC requires a deadline and `authorization: Bearer $SF_GAMEPLAY_TOKEN`; the fixture generates a new token for each run. This development credential is not the DEC-04 session protocol. The host uses only centrally pinned packages and has its own lock file.

Required environment: `GAMEPLAY_HOST_PORT` (1..65535), `SF_GAMEPLAY_TOKEN`, `GAMEPLAY_LEDGER_CONNECTION`, `GAMEPLAY_CHARACTER_CONNECTION`, `GAMEPLAY_HOUSING_CONNECTION`, `GAMEPLAY_EXCHANGE_CONNECTION`, and `GAMEPLAY_CONTENT_ROOT` (parent of `loot/`, `quests/`, `crafting/`, and `world/`). Connection strings may point to the same PostgreSQL database with the four owned schemas. Run from the repository root with the pinned SDK:

```powershell
& Artifacts/Persistence/Toolchains/dotnet-10.0.402/dotnet.exe run --project BackendServices/Gameplay.Host --locked-mode
& tools/Test-GameplayHosts.ps1 -EvidenceRoot "$PWD/Artifacts/Persistence/GameplayHosts/review-01"
```

The housing gameplay migration `BackendServices/Housing.Postgres/Schema.Gameplay.sql` follows the existing version 3 schema, requires an empty claim set, and advances the marker to version 4. Existing claims need a geometry backfill before that migration. The store owns plot geometry, admission serialization, placement debit reconciliation, removal reservations, refund receipt matching, and operation replay. The legacy `expected_world_revision` request field is ignored: the database advisory lock serializes admission, so clients need no undiscoverable world counter. Claim size and spacing use `ClaimSettings`; removal refunds use `PlacementRefundSettings` and the typed `HousingRefundRounding.UpToWholeUnit` rule for positive fractional integer bundles. Their shipped defaults, safe bounds, units, permission and effective-time rules remain in the domain declarations and shared configuration workflow. This host reads one default snapshot per operation; it does not add a console override.

Status codes come from typed rejection codes: `OK` for accepted/replayed results, `ALREADY_EXISTS` for operation ID conflicts, `PERMISSION_DENIED` for territory, build and contributor denials, `FAILED_PRECONDITION` for stale revisions and other gameplay rejections, `UNAVAILABLE` for store/schema outages, `INVALID_ARGUMENT` for malformed requests, `UNAUTHENTICATED` for token failure, and `DEADLINE_EXCEEDED` for an expired call. The host passes the call cancellation token and remaining deadline to housing database work and does not report a late deadline after a successful commit. A client retries the identical source or operation ID after an ambiguous outcome. Each service has a separate executable wire test project under `Gameplay.Host.Tests/`.

The fixture provisions an owned disposable PostgreSQL cluster, runs all four services through gRPC, restarts the host, repeats durable receipts, stops PostgreSQL, and checks outage mapping. Its housing leg uses the fixture-only `SF_GAMEPLAY_FAULT_AFTER_REMOVE_GRANT` operation ID to stop the host after a committed refund, immediately restarts PostgreSQL, and checks one recovered result; it also checks a stale container revision followed by a new removal ID and concurrent place/remove. The environment variable is cleared before the recovery host starts. The fixture's journey seeds harvest grants and performs content-validated crafting through gRPC; progression, quest, claim, placement, and reward calls travel through gRPC. Crafting now travels through the gRPC contract with durable Convert replay. Progression and quest are two durable receipt transactions, so a retry repairs a failure between them. Quest completion pays the item lines authored in content/quests/greenlands_frontier_founder.json into the character backpack under a persisted deterministic Grant intent. Reward eligibility facts are supplied by the trusted server; denied defeat decisions are only cached for this host lifetime.

Crafting checks character ownership, shipped recipe and count (1..20) before InventoryLedger `Convert`. The ledger replays the operation receipt before comparing an old container revision. Quest progress and its reward intent commit together; the host saves the character's unique backpack ID and pays all authored item lines in one serialized InventoryLedger store transaction and one Grant receipt under the quest/step/character/bundle operation ID. A matching committed Grant receipt marks the intent Complete and the additive `granted_items` reply lists every item and quantity. After an interrupted payout, a missing receipt is reissued under that same ID using the latest container revision; ledger serialization and receipt replay prevent double payment. A full backpack returns `FAILED_PRECONDITION` and leaves the intent Pending for sweeper retry after space frees; the transaction grants all lines or none. Missing or changed backpacks also leave the intent Pending. Reward intents store the quest content revision and expanded item lines in the quest transaction. Recovery grants that snapshot even after content changes. CharacterState schema version 2 rejects older markers; `Schema.RewardSnapshot.sql` upgrades only stores with no existing reward intents.

The hosted recovery loop runs every two seconds and ages intents for five seconds (typed shipped operational defaults; bounds 1 second..5 minutes and 2 seconds..10 minutes). A session PostgreSQL advisory lock permits only one host to sweep at a time. It reconciles placements, removals and reward grants and logs one `GAMEPLAY_SWEEP` line per resolution. Placements with absent debit receipts are fenced by the housing ledger tombstone; removals use their existing refund receipt. Housing removals have no timestamp, so they are resolved on the next sweep. Exchange pending listing settlements are reconciled under the same advisory lock. Pending trade offers expire after a shipped five-minute lifetime (bounds 30 seconds..one hour) and return escrow; active listings use the Exchange domain duration control. Trade offers require pre-funded item escrow. `ListItem` moves items to escrow before creating the listing. Those are two durable transactions, so a crash between them needs an operator reconciliation path not implemented in this host-only scope. The host does not expose a currency faucet. The recovery timing is code delivered and has no console override.
