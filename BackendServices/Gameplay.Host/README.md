# Gameplay gRPC host (INT-04 preparation)

Gathering `GetNode` and `HarvestWithIntent` use `PostgresGatheringStore` in the inventory database. Apply `InventoryLedger.Postgres/Schema.GatheringNodes.sql` after `Schema.Outbox.sql` before starting these hosts and grant the runtime identity DML on its tables. The migration stores the complete growth clock state and immutable harvest receipts. `HarvestWithIntent` requires backpack identity and serialized INT-06 follow-up bytes; the node mutation and pending grant intent commit together, and host recovery grants the item once through the ledger, which queues the progression follow-up. An older host returns `UNIMPLEMENTED` for this distinct method before any mutation. The new host refuses legacy `Harvest`; InventoryLedger.Host refuses client-first `Source=gathering` grants once the migration is installed. `tools/Test-GameplayHosts.ps1 -GatheringOnly` exercises old-host refusal, round trip, restart, both crash gaps and immature-node charges.

INT-06 backend: `InventoryLedger.GrantWithIntent` requires an immutable ApplyReceiptRequest intent. The originating grant and intent commit together; this host relays pending intents on startup and a bounded poll, with leases, per-character ordering, retry and parking. The earlier Unreal ledger grant path supplies that intent, but its separate node Harvest call must move to the new host-owned grant flow before durable node harvesting is playable. See `docs/decisions/INT-06-durable-receipt-outbox.md` for the relay and remaining LiveOps control integration.

Run `Gameplay.Host.dll outbox-status` with `GAMEPLAY_LEDGER_CONNECTION` to inspect pending/parked counts and effective shipped controls. The host logs the same values each poll. Batch size 32 rows (1–256), poll interval 2 seconds (1–60), and max attempts 12 (1–100) are declared in `ReceiptOutboxControls`; shared config publication and GM/web presentation remain outside this development host. The `SF_GAMEPLAY_FAULT_BEFORE_OUTBOX_SEND` operation ID is only a disposable fixture crash hook.

An operator with the ledger connection can run `Gameplay.Host.dll outbox-requeue <source-operation-id>` after reviewing the parked error. It resets that row's attempt counter and due time while preserving its original payload, digest, source ID and character order. It refuses pending, leased and delivered rows. This development CLI uses the database credential supplied to the process; production operator identity, audit and approval must come from the shared operations workflow before it is exposed remotely. A requeued row may fail again and park; inspect `outbox-status` afterward.

One ASP.NET Core HTTP/2 process serves six versioned protobuf services: Rewards, Gathering, Progression (including quest evidence), Housing, Crafting, and Exchange. It binds only `127.0.0.1:$GAMEPLAY_HOST_PORT`. Every RPC requires a deadline and `authorization: Bearer $SF_GAMEPLAY_TOKEN`; the fixture generates a new token for each run. This development credential is not the DEC-04 session protocol. The host uses only centrally pinned packages and has its own lock file.

Progression `CreateCharacter` requires a v2 appearance packet with a face index. The host loads `content/appearance/human.json` once at startup, validates against that allowlist (no cosmetic catalogue or ownership integration yet), and saves the bytes at appearance revision 1. Invalid or absent packets return `INVALID_ARGUMENT: APPEARANCE_INVALID`. `GetCharacterState` returns the stored packet and its allowlisted face ID; characters without appearance return `Orlando` and no packet. Run `tools/Test-GameplayHosts.ps1 -EvidenceRoot <fresh GameplayHosts child> -AppearanceOnly` for the three focused wire cases.

MKT-01: `MarketCatalog` loads each town's market content at startup; only an open market and its allowlisted base or CRF-01 grade IDs can be listed. The host derives fair value, 1% listing fee and 5% sale fee; it ignores caller fee fields, caps a unit price at 20 times the content fair value, and limits a listing to 100 units by the typed control. A 1 copper minimum fee reconciles the spec's small 80 copper example with its conflicting 100 copper minimum fee line; a 1 copper total listing is refused because the fee would consume it. This is an alpha default for new listings, subject to the shared configuration publication workflow. The starter purse remains 500 copper, once per character when `GAMEPLAY_ALPHA_STARTER_KIT=on`. `Exchange.Tool` validates a market directory; `Exchange.Tool.Tests` checks grade values, denied goods and unknown markets. The plain Silverbrook marker is spawned on terrain at the Market Square south edge, and the zone server checks the player's reach before it sends market intents. Art and full live market listing refresh remain in the UI session.

CRF-01: Craft reads CharacterState skills and known recipes, refuses an unknown recipe, converts selected input grades to one graded output, and returns score/grade/discovery. The HMAC seed derives from the host's per-run bearer token in this development fixture; keep the token stable across a host restart so a pending craft can replay. `LearnRecipe` accepts trainer or scroll sources; a CharacterState intent is written first, then Exchange sinks the trainer fee or InventoryLedger consumes the scroll, and the recovery sweep finishes the knowledge snapshot after interruption. The 250-difficulty trainer recipe costs 125 copper at the shipped 0.5-copper rate. A same-id replay retains its receipt; an already-known recipe leaves a new scroll untouched. The owner chose crafts to never fail, unknown recipes listed with a learning hint, and difficulty-scaled trainer fees. The content/UI surface uses those rules; no new art is introduced.

Connection pools are release-declared operating controls in `DatabasePoolSettings`: InventoryLedger 24 connections (allowed 2..32), CharacterState 12 (2..24), Housing 24 (2..24), Exchange 16 (2..24), all per host process. Each role has a separate application name and pool, with zero preopened idle connections. Units are PostgreSQL client connections. The safe fallback is the shipped default; the effective value is logged/inspectable through PostgreSQL `pg_stat_activity.application_name`. Only realm configuration operators may change a bound through a reviewed shared configuration publication; activation is on host restart. This development host currently consumes the shipped snapshot and has no editable console field. Connection string pool fields are replaced by the declared limits. Topology, credentials, and transaction rules stay release-controlled. Size the sum across host replicas, the InventoryLedger host, administrative connections, and PostgreSQL reserved slots before deployment.

Transaction-mode pooling remains disabled. The recovery worker owns a session advisory lock for a complete sweep and returns it explicitly; PgBouncer transaction mode cannot preserve that lock. The outbox relay releases each database call before its gRPC await, and store transactions do not span gRPC calls. A pooler requires a redesigned sweep leadership lease and a measured isolated ramp before it can enter the capacity fixture or ops profile.

The housing gameplay migration `BackendServices/Housing.Postgres/Schema.Gameplay.sql` follows the existing version 3 schema, requires an empty claim set, and advances the marker to version 4. Apply `Schema.Geometry.sql` next for BLD-01 shape identity and version 5, then `Schema.Construction.sql` for the DEC-02 decision column and version 6. Existing claims need a geometry backfill before the v4 migration. `Place` is the DEC-02 coordinator: `Begin`, inventory reserve into the builder's hold, `Decide`, then `Finish` (debit or release). `GAMEPLAY_ALPHA_STARTER_KIT` (empty or `on`) credits the Alpha Starter Kit purse (`PurseCopper`, default 500, bounds 0–10,000) once per character on `GetCharacterState`, the restore on connect. It uses `Exchange.Credit` at `alpha-starter-kit/v1/<character>/purse` with source `starter_kit`. `SF_GAMEPLAY_FAULT_AFTER_PLACE_DECISION=<operation id>` is a fixture fault that kills the host after the commit decision is durable; the sweeper rolls it forward. The store owns plot geometry, admission serialization, placement decisions, removal reservations, refund receipt matching, and operation replay. The legacy `expected_world_revision` request field is ignored: the database advisory lock serializes admission, so clients need no undiscoverable world counter. Claim size and spacing use `ClaimSettings`; removal refunds use `PlacementRefundSettings` and the typed `HousingRefundRounding.UpToWholeUnit` rule for positive fractional integer bundles. Their shipped defaults, safe bounds, units, permission and effective-time rules remain in the domain declarations and shared configuration workflow. This host reads one default snapshot per operation; it does not add a console override.

`Housing.ListStructures(claim_id)` returns the committed structures and the claim's structure revision from one serialized store read; removed and pending structures are excluded. `Housing.Grant` accepts the ClaimTerritory right bits (build=1, open doors=2, use containers=4). An empty mask removes the target's grant; a nonempty mask replaces that target's prior mask. Only the owner may grant. The expected permission revision is a CAS fence, and the durable `SaveClaim` operation receipt returns the original reply on an identical operation replay, including after restart. Grant changes the claim and permission revisions, so subsequent Place/Remove calls need the new permission revision. These RPCs add no session authentication beyond the host's existing development bearer credential; the Unreal session must supply authenticated actor identity until DEC-04 is integrated.

Status codes come from typed rejection codes: `OK` for accepted/replayed results, `ALREADY_EXISTS` for operation ID conflicts, `PERMISSION_DENIED` for territory, build and contributor denials, `FAILED_PRECONDITION` for stale revisions and other gameplay rejections, `UNAVAILABLE` for store/schema outages, `INVALID_ARGUMENT` for malformed requests, `UNAUTHENTICATED` for token failure, and `DEADLINE_EXCEEDED` for an expired call. The host passes the call cancellation token and remaining deadline to housing database work and does not report a late deadline after a successful commit. A client retries the identical source or operation ID after an ambiguous outcome. Each service has a separate executable wire test project under `Gameplay.Host.Tests/`.

The fixture provisions an owned disposable PostgreSQL cluster, runs all four services through gRPC, restarts the host, repeats durable receipts, stops PostgreSQL, and checks outage mapping. Its housing leg uses the fixture-only `SF_GAMEPLAY_FAULT_AFTER_REMOVE_GRANT` operation ID to stop the host after a committed refund, immediately restarts PostgreSQL, and checks one recovered result; it also checks a stale container revision followed by a new removal ID and concurrent place/remove. The environment variable is cleared before the recovery host starts. The fixture's journey seeds harvest grants and performs content-validated crafting through gRPC; progression, quest, claim, placement, and reward calls travel through gRPC. Crafting now travels through the gRPC contract with durable Convert replay. Progression and quest are two durable receipt transactions, so a retry repairs a failure between them. Quest completion pays the item lines authored in content/quests/greenlands_frontier_founder.json into the character backpack under a persisted deterministic Grant intent. Reward eligibility facts are supplied by the trusted server; denied defeat decisions are only cached for this host lifetime.

Crafting checks character ownership, shipped recipe and count (1..20) before InventoryLedger `Convert`. The ledger replays the operation receipt before comparing an old container revision. Quest progress and its reward intent commit together; the host saves the character's unique backpack ID and pays all authored item lines in one serialized InventoryLedger store transaction and one Grant receipt under the quest/step/character/bundle operation ID. A matching committed Grant receipt marks the intent Complete and the additive `granted_items` reply lists every item and quantity. After an interrupted payout, a missing receipt is reissued under that same ID using the latest container revision; ledger serialization and receipt replay prevent double payment. A full backpack returns `FAILED_PRECONDITION` and leaves the intent Pending for sweeper retry after space frees; the transaction grants all lines or none. Missing or changed backpacks also leave the intent Pending. Reward intents store the quest content revision and expanded item lines in the quest transaction. Recovery grants that snapshot even after content changes. CharacterState schema version 3 rejects older markers; `Schema.RewardSnapshot.sql` upgrades only stores with no existing reward intents.

The hosted recovery loop runs every two seconds and ages intents for five seconds (typed shipped operational defaults; bounds 1 second..5 minutes and 2 seconds..10 minutes). A session PostgreSQL advisory lock permits only one host to sweep at a time. It reconciles placements, removals and reward grants and logs one `GAMEPLAY_SWEEP` line per resolution. Placements with absent debit receipts are fenced by the housing ledger tombstone; removals use their existing refund receipt. Housing removals have no timestamp, so they are resolved on the next sweep. Exchange pending listing settlements are reconciled under the same advisory lock. Pending trade offers expire after a shipped five-minute lifetime (bounds 30 seconds..one hour) and return escrow; active listings use the Exchange domain duration control. Trade offers require pre-funded item escrow. `ListItem` records a pending Exchange intent before moving items to escrow. The sweeper resolves the durable transfer receipt into an active listing or tombstones an absent transfer after the shipped recovery window. The host does not expose a currency faucet. The recovery timing is code delivered and has no console override.

INT-05 position: Apply CharacterState/Postgres Schema.Position.sql after v2 to advance the marker to v3. Progression.SavePosition validates a lowercase zone key, finite coordinates within +/-10,000,000, and yaw within +/-360 degrees. First save expects revision 0; later saves use the returned revision. Stale revisions return FAILED_PRECONDITION. GetCharacterState omits position before the first save and returns active-step objective counts, including zero counts. Position revision is independent of quest and XP revisions. The caller chooses the save interval and world bounds; this development host uses its existing bearer identity.
