# PostgreSQL inventory ledger store

`PostgresInventoryLedgerStore` implements the existing `IInventoryLedgerStore` callback. Install `Schema.sql`, then the additive `Schema.Outbox.sql` migration with a migration identity before constructing it; the runtime connection needs schema usage, table DML, and SELECT on `inventory.schema_version`. The installed marker is version 2 with the reviewed checksum of the migration DDL prefix. Every ledger transaction checks the marker before reading or writing; missing, inaccessible, unknown, or newer versions throw `LedgerSchemaCompatibilityException` and roll back. Each transaction locks its operation key, then its touched container rows in sorted ID order. It loads receipts by operation ID and containers on demand, and commits revisions, quantities, and new receipts together. Enumeration loads every container but no receipt history. Container revision updates use compare-and-set. A retry after commit reads the persisted operation ID and returns its original receipt. Connection, deadlock, and database failures throw `LedgerStoreUnavailableException`; callers should retry the same operation ID after recovery. No state is held or published in memory on failure.

The receipt primary key and per-operation advisory lock fence replay before stale revision checks; a duplicate insert remains a rejected SQL constraint error. SQL data and constraint errors (classes 22 and 23) reject the operation; transient, connection, rollback, and operator-intervention errors remain retryable. Production migration rollout remains separate; update the versioned schema and runtime compatibility policy together before applying a migration. This project adds no adjustable balance or operating value. Container capacity remains the existing bounded, trusted `ContainerSpec` value.

Container reads take a separate per-ID advisory lock before the row lock, including when the row is absent, so concurrent creation of one specification returns the committed view. Owner and kind lookups use a plain indexed SELECT without locking container rows; mutations read the selected container again under its normal lock. Existing version-1 installations need the owner lookup index applied through their normal migration rollout to receive the lookup performance benefit.

For a quiesced, synthetic loopback ledger, `tools/Backup-InventoryLedger.ps1` creates a custom-format `pg_dump` plus `manifest.json` with SHA256, schema version, and row counts. Supply `-OutputDirectory <fresh path> -HostName 127.0.0.1 -Port <port> -Database <name> -Username <role>` and `PGPASSWORD` in the caller environment. `tools/Restore-InventoryLedger.ps1 -BackupDirectory <backup> -InstanceRoot <fresh Artifacts/Persistence/InventoryLedgerDurable child>` verifies the hash before creating a fresh owned PostgreSQL instance/database, then checks marker, counts, entry/container references, receipt references, and contiguous container revision history. It writes synthetic credentials only to the ignored instance directory; `-InstanceRoot <same path> -Cleanup` stops and removes that owned instance. The manifest is an integrity check, not an authenticity signature; keep backup and manifest under trusted access control. This fixture does not establish production RPO/RTO, encryption, or a multi-domain restore process.

Run the owned synthetic loopback fixture from the repository root with a fresh child path:

```powershell
& tools/Test-InventoryLedgerDurable.ps1 -EvidenceRoot "$PWD/Artifacts/Persistence/InventoryLedgerDurable/review-01"
```

The wrapper verifies the pinned SDK and PostgreSQL tools, restores with committed package locks and the existing Npgsql 10.0.3 pin, creates a new local cluster, uses generated credentials passed to the test executable through its environment, runs the test executable across immediate PostgreSQL stops and restarts, backs up at a known ledger revision, writes more, restores to a second owned cluster, rejects a flipped-byte backup, and checks newer-schema refusal. It removes both owned clusters. It does not connect to a shared or remote database. The fixture is synthetic; no listener, production authentication, or cross-domain transaction coordinator is included.

INT-06: a Grant with a version-1 follow-up intent commits the exact serialized progression request, SHA-256 digest and operation receipt atomically. The host validates character and operation identity. The Gameplay relay drains on startup and every 2 seconds, claims up to 32 with a 30-second lease, preserves per-character order, and parks after 12 attempts or a permanent identity/payload error. Batch size (1-256 rows), poll interval (1-60 seconds), and max attempts (1-100) are typed release-declared controls with defaults 32, 2 seconds and 12. Pending and parked counts are logged by Gameplay.Host. The shared LiveOps config and operator surfaces are not implemented in this backend repository; publishing controls there remains an integration step. Delivered tombstones and pending/parked rows are retained. Backups include the outbox table.
