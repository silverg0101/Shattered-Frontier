# Backend capacity harness

Run through `tools/Test-Capacity.ps1`. The harness uses the pinned Gameplay.Host gRPC client and PostgreSQL dependencies. It creates one backpack per synthetic character (and an escrow container for traders). Fixture grants stand in for the missing gathering RPC and are excluded from measured RPC latency. The reconnect lane opens a fresh HTTP/2 channel and reads character state; it does not measure Unreal movement or replication. All roles use stable per-character operation IDs and deterministic think-time jitter.

The milestone controls the gate sizes, 15-minute measured window, role mix, and pass budgets. Harness-only settings are typed command options: seed defaults to 20261021 (integer 0..2147483647), warmup to 30 seconds (0..300), measured duration to 900 seconds (1..7200), and think time to 1000 milliseconds (100..5000). They apply at process start and are local load-generator controls, not gameplay balance or operator configuration. The fixture script uses 50 ms client delay to emulate the specified round-trip component and reports it separately; local loopback traffic itself has no 50 ms network RTT. Short durations support development checks and cannot be claimed as milestone gates.

The direct PostgreSQL audit checks per-operation uniqueness, receipt change sums against live inventory (including escrow), committed housing debits/refunds, quest completion reward uniqueness, and wallet balances against entry sums. It fails closed on pending housing or reward operations. It does not prove crash/recovery, Unreal load, real-client rendering, network replication, or a two-hour soak.

After measured work stops, an initially failed audit is retried every two seconds for at most 30 seconds to let committed intents reconcile. The report records `auditDrainSeconds`; any mismatch or pending row after that bound still fails the gate. The measured RPC window and its latency samples end before this drain.

Participant backpack and claim setup finishes before the warmup clock starts. Claim creation is limited to eight concurrent fixture calls so its globally serialized admission does not exhaust the short setup RPC deadline. The first activity cycle is deterministically spread across the think interval after the barrier. These fixture gates do not change the participant role mix or one-cycle-per-participant measured load.

After an ambiguous builder RPC, the load generator reads `Housing.ListStructures` and refreshes that claim's revision. Gather and fight roles likewise refresh `Progression.GetCharacterState` after an RPC failure. A failed measured RPC remains an error in the report. This prevents a warmup reply loss followed by successful server commit from making every later measured request stale.
