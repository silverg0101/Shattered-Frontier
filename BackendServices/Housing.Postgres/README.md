# PostgreSQL housing store

BLD-01 geometry identity uses the additive `Schema.Geometry.sql` migration after gameplay v4, advancing Housing to v5. It adds `shape_key` and `orientation_index` to placements. Existing rows become `legacy.generic` at identity index 0, preserving the current generic cube reconstruction. New clients send a BLD-01 canonical shape key (ASCII `[a-z0-9._-]+`, 1–128 characters) and an orientation index in 0–23 (0 is identity; 1–23 sort the remaining proper signed-axis rotations by their ordered +X,+Y,+Z images); older proto clients omit both and receive the same defaults. The host validates before inventory access and the database enforces the bounds. This contract stores the supplied key and orientation; it does not yet load a compiled shape manifest to verify the key's existence or the shape-specific rotation allowlist. The Unreal consumer must map the key to its shipped canonical geometry before exact reconstruction.

`PostgresHousingStore` durably stores claims, character build grants, funded/grace/notice deadlines, claim revision receipts, claim-scoped structure revisions, and pending/committed/compensated placement records. Install `Schema.sql`, `Schema.Gameplay.sql`, then `Schema.Geometry.sql` with a migration identity. The runtime role needs schema usage, table DML, and marker read access. Every call checks exactly the version 5 marker and refuses missing, inaccessible, or other versions. Claim admission retains a transaction advisory lock for the spacing and entitlement scan; placement and removal decisions lock their claim's structure revision row before replay or nested inventory work. Claim edits use revision compare-and-set and confirmed placements advance the current structure revision. SQL classes 22 and 23 are non-retryable `HousingRejectedException`; connection failure is `HousingUnavailableException` and the same operation ID should be retried. The database stamps `created_at` on each placement; callers cannot supply it through `Begin`.

The shared backup and restore tools accept pending placements only while `created_at` is within the bounded recovery window. The housing-owned operating declaration is `housing.pending_placement_recovery_window` (registry proposal): **Pending placement recovery window**, integer seconds, shipped default 3600 seconds (one hour), allowed 60–86400 seconds in whole-second steps, fallback 3600 seconds, realm scope, applied to the next backup or restore invocation, restricted to backup operators with the normal operations approval tier. The tools expose it as `-PendingPlacementRecoveryWindowSeconds`; they inspect the effective value through that typed invocation. A production control must be published through the shared config-service draft/review workflow before it can become live editable; these fixture tools do not provide a gameplay console override. Operators must recover or compensate older pending placements before backup or restore. A younger row still needs reconciliation after restore; this check does not schedule it.

`SaveClaim` accepts an authoritative claim snapshot, expected revision, operation ID and fingerprint. It persists grants and lifecycle timestamps but does not calculate territory geometry or advance timers; `ClaimTerritory` remains the rules owner. It returns the original snapshot on an exact operation retry. `Begin(request, now)` checks the stored build grant, permission revision and structure revision before reserving a unique structure ID and cell. Build is allowed in Active before `funded_until` and in Grace; other states are denied. The caller must validate content/cost against the release-shipped recipe catalog and authenticate actor, claim and container ownership before `Begin`; this storage boundary does not perform those checks. A retry with the same operation ID returns its stored placement decision.

The placement coordinator must call `Begin` before the ledger debit, use `operationId + "/consume"` as its durable inventory operation ID, then call `Reconcile`. `Reconcile` reads the ledger's durable operation receipt inside one ledger transaction: a matching debit commits the reserved structure and advances its current revision, while a missing debit writes a zero-change `housing/compensated` operation at that key and closes the pending row as compensated without issuing a refund. The ledger fingerprint check rejects a late consume. A ledger outage leaves the row pending. A mismatched receipt, including its prior container revision, is refused for manual reconciliation. The reservation prevents a second placement from winning its cell. A production authority adapter, cross-service atomicity, and automatic recovery scheduling remain to be built. No guessed refund is issued.

Removal uses the same durable decision pattern at `operationId + "/refund"`. A confirmed matching grant removes the piece; a missing grant is fenced with a zero-change `housing/compensated` tombstone in the ledger transaction and marks the removal `Compensated`. Only pending and committed removals reserve a placement, so a fresh operation ID can retry after compensation. Host startup reconciles pending removals, including grants committed before a crash. A ledger outage leaves them pending. Refund quantities stay integral: the typed `HousingRefundRounding.UpToWholeUnit` rule rounds a positive fractional refund up to one unit (one bundle at 50% returns one); zero percent returns zero. The percent values remain the bounded `PlacementRefundSettings` snapshot. Exact committed placement replays return their stored receipt before content or ownership checks.

Run the owned synthetic loopback fixture from the repository root with a fresh child path:

```powershell
& tools/Test-HousingDurable.ps1 -EvidenceRoot "$PWD/Artifacts/Persistence/HousingDurable/review-01"
```

The fixture uses pinned .NET and PostgreSQL, the existing pinned Npgsql package, generated per-run credentials passed through child environment variables, immediate-stop restart, outage and newer-schema refusal, and removes its owned cluster. It does not use a shared or remote database.

StructureSnapshot holds a shared lock on the claim structure revision while reading its placements, keeping the revision and list from one committed structure state.
